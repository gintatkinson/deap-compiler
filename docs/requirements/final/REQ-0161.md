### REQ-0161: Epics Projection: Structural Decomposition & Subsystem Capability Mapping

#### 1. Normative Statement

The downstream specification projection engine and structural decomposition framework of Subsystem 9 shall synthesize high-level Epic specifications by partitioning the sovereign AST model graph along top-level subsystem boundaries and projecting formal Subsystem Capability Allocations mapping every SysML v2 `capability def` block to its owning subsystem. The projection engine shall generate an Epic specification document for each top-level subsystem package or architectural assembly, cataloging its constituent structural decomposition hierarchy, allocated capabilities, functional objectives, and boundary interfaces. If any capability definition within the model fails to be allocated to an owning subsystem, if an unresolvable or undefined subsystem is referenced, or if multiple conflicting primary subsystem allocations are asserted without disambiguation, the compiler shall fail closed and emit diagnostic error code `E0500`.

  Specifically, the downstream projection engine, structural partitioning framework, and capability allocation mapper shall strictly enforce the following structural, algebraic, and operational provisions across all compilation units:
  1. **Top-Level Subsystem Structural Decomposition & Model Partitioning**:
     - The compiler shall identify all top-level architectural subsystem packages and composite component definitions in the AST $`\mathcal{S} = \{S_1, S_2, \dots, S_m\}`$ derived from root package classifiers and composite assemblies in accordance with REQ-0021, REQ-0070, and REQ-0071.
     - Each top-level subsystem $`S_k \in \mathcal{S}`$` shall form the architectural root and scope boundary for exactly one synthesized Epic specification document `$`E_k \in \mathcal{E}`$.
     - The set of Epics $`\mathcal{E} = \{E_1, E_2, \dots, E_m\}`$` shall be ordered deterministically according to canonical lexicographical ASCII byte ordering of fully qualified symbol names (`$`\prec_{\text{lex}}`$, REQ-0032) or deterministic dependency DAG topological sorting (REQ-0048).
     - If two distinct subsystems resolve to identical qualified names or produce an Epic document identifier collision, the compiler shall deterministically fail closed and emit diagnostic error code `E0500` (`EpicIdentifierCollision`).
  2. **Subsystem Capability Allocation Mapping**:
     - The engine shall ingest every SysML v2 `capability def` (and KerML behavioral capability element) from the model capability set $`\mathcal{M}_{\text{capabilities}}`$.
     - Ownership and allocation of capability $`c \in \mathcal{M}_{\text{capabilities}}`$` to subsystem `$`S_k \in \mathcal{S}`$ shall be resolved through:
       - *Lexical Containment*: The capability definition or usage is declared directly within the lexical scope or package hierarchy of subsystem $`S_k`$ (REQ-0040, REQ-0041).
       - *Explicit SysML v2 Allocation (`allocation def` / `allocate` usage)*: An explicit allocation relationship (`allocate c to S_k;` per REQ-0077) binds the capability to subsystem $`S_k`$.
       - *Behavioral Realization & Performance Hooks*: A subsystem part or action performs or satisfies the capability contract (`satisfy` per REQ-0086 or `perform` per REQ-0069).
     - Resolution Precedence: Explicit allocation relationships take precedence over lexical containment if both are present and congruent; if contradictory explicit allocations designate disjoint primary owning subsystems for the same capability without an explicit primary allocation qualifier, the compiler shall fail closed and emit diagnostic error code `E0500` (`DuplicateCapabilityAllocation`).
  3. **Exact Capability Partition Invariant (Completeness & Disjointness)**:
     - *Completeness*: Every declared capability $`c \in \mathcal{M}_{\text{capabilities}}`$ must be allocated to at least one subsystem Epic:

```math
\bigcup_{k=1}^m E_k = \mathcal{M}_{\text{capabilities}}
```

       If any capability remains unallocated, the compiler shall fail closed and emit diagnostic error code `E0500` (`UnallocatedCapabilityViolation`).
     - *Disjointness*: The capability sets allocated across distinct Epics must be mutually disjoint:

```math
E_i \cap E_j = \emptyset \quad (\forall i \ne j)
```

       No single capability may belong to more than one primary subsystem Epic.
     - *Subsystem Grounding*: If an allocation references a target subsystem not present in the declared subsystem set $`\mathcal{S}`$, the compiler shall fail closed and emit diagnostic error code `E0500` (`OrphanedSubsystemCapability`).
  4. **Subsystem Capability Allocation Roster & Table Format**:
     - Each Epic specification document shall include a formal Subsystem Capability Allocation table.
     - Each capability allocation row maps:

```math
\text{Allocation}(c) = \langle \text{CapabilityName}, \text{SubsystemPackage}, \text{DescriptionObjective} \rangle
```

     - The tabular projection shall catalog the following attributes for every allocated capability $`c`$:
       - *Capability Identifier*: The interned symbol identifier ($`\text{name}(c) \in \mathcal{S}_{\text{intern}}`$).
       - *Capability Fully Qualified Name*: The canonical scoped path ($`\text{FQN}(c)`$).
       - *Owning Subsystem*: The fully qualified path of the owning subsystem ($`\text{FQN}(S_k)`$).
       - *Objective / Description*: Textual objective or specification prose normalized to eliminate raw carriage returns, escape Markdown delimiters, and preserve multi-line token semantics (REQ-0018).
       - *Deterministic UUIDv5 Anchor*: The persistent 128-bit identity anchor ($`\Delta_c`$, REQ-0010, REQ-0159).
       - *Source Provenance*: Lexical source file byte spans ($`\text{span}_c`$, REQ-0002).
  5. **Epic Specification Document Structure**:
     - Every generated Epic specification document shall be structured with the following standardized sections:
       - *YAML Frontmatter*: Containing deterministic RFC 4122 UUIDv5 anchor, fully qualified subsystem path, epic identifier, title, subsystem index, creation hash digest, and artifact type `epic_specification` (REQ-0159).
       - *Subsystem Executive Overview & Purpose*: Extracted from doc comments or metadata annotations of the subsystem package (`doc /* ... */` or `@doc`).
       - *Structural Decomposition Hierarchy*: Hierarchical nested listing or tree of constituent child parts, sub-components, ports, and internal interconnections (REQ-0071, REQ-0072).
       - *Subsystem Capability Allocation Table*: Canonical Markdown table projecting the complete capability allocation roster for the subsystem.
       - *Boundary Interface & Interconnect Summary*: Cross-references to Level 1C Interface Control Documents (Subsystem 8, REQ-0145, REQ-0148) cataloging external ports and connecting channels.
  6. **Hierarchical Subsystem Flattening & Multi-Level Decomposition**:
     - In hierarchical systems containing nested sub-packages or multi-level assembly tiers ($`S_{k.1}, S_{k.2}`$), the projection engine shall support:
       - Flattening of child capabilities into the enclosing top-level subsystem Epic, with the internal qualified subsystem path recorded in the allocation table, or
       - Controlled hierarchical Epic decomposition where nested subsystems project child Epic sections while preserving global partition disjointness.
  7. **Streaming Artifact Sink Interface ($`O(1)`$ Buffer Memory)**:
     - All generated Epic specification documents shall be emitted directly through the streaming artifact sink interface (REQ-0162, REQ-0177) with strictly bounded $`O(1)`$` resident memory buffer overhead relative to total generated specification size `$`|A|`$, streaming markdown chunks to the filesystem without buffering complete document corpora in resident heap memory.
  8. **Compliance with the 5 Executive Architectural Directives**:
     - *Directive 1 (Deterministic UUIDv5 Anchors)*: Every generated Epic document, structural decomposition node, capability allocation record, and table row shall bind an immutable RFC 4122 UUIDv5 identifier hashed from the canonical DEAP namespace OID and node fully qualified topological path ($`\text{UUIDv5}(\text{OID}_{\text{DEAP}}, \text{FQN}(n))`$) in accordance with REQ-0010 and REQ-0159. Time-based UUIDs are strictly banned.
     - *Directive 2 (Bounded Work-Stealing Parallelism)*: Parallel AST partitioning, capability resolution, and Epic Markdown serialization across independent subsystems shall execute strictly on a centralized, bounded work-stealing thread pool with worker upper bound $`N_{\text{max\_workers}}`$ in accordance with REQ-0012. Unbounded dynamic thread spawning is strictly banned.
     - *Directive 3 (String Interner Memory Allocation Exception)*: Subsystem names, capability identifiers, package paths, and objective strings shall be interned into the deduplicated global symbol interner pool during lexical analysis per REQ-0036 as the sole permitted exception to zero-copy memory management.
     - *Directive 4 (Synchronization Token Error Recovery)*: The projection engine shall implement synchronization token error recovery on statement delimiters (`;`, `}`) and table row delimiters (`|`) in accordance with REQ-0013 and REQ-0016. When semantic violations occur (`E0500`), diagnostics shall accumulate in the preallocated error sink buffer $`\mathcal{D}_{\text{sink}}`$`, substitute typed error sentinels (`$`\bot_{\text{alloc}}`$`), and continue partitioning subsequent subsystems. If accumulated diagnostics reach capacity `$`C_{\text{max\_errors}}`$, terminal diagnostic `E0199` shall be emitted and compilation halted gracefully.
     - *Directive 5 (Panic-Free Release Paths & Benchmarking Isolation)*: The projection engine shall strictly enforce a deterministic, non-panicking execution contract with total-function error handling. Epic projection latency ($`\lt 25\text{ ms}`$` for `$`|C| + |S| = 10^4`$` model elements) and peak RSS memory (`$`\lt 100\text{ MB}`$) performance gates shall be evaluated exclusively in compiled Release mode (`--release`) under dedicated benchmark harnesses isolated from CI logic tests in accordance with REQ-0011 and REQ-0196.
  9. **Pure Abstract Schema Invariant**:
     - All diagnostic messages, test models, and illustrative examples shall strictly employ synthetic abstract MBSE placeholders (`Package_0`, `Package_1`, `Subsystem_0`, `Subsystem_1`, `Subsystem_Alpha`, `Subsystem_Beta`, `Capability_0`, `Capability_1`, `Capability_Alpha`, `Capability_Beta`, `Part_0`, `Port_0`, `param_x : Real`), strictly prohibiting hardcoded domain concepts, mock data, and non-ASCII dashes.

#### 2. Formal Invariant

Let $`\mathcal{V}_{\text{AST}}`$` denote the universe of allocated AST nodes in contiguous bump arena storage, and let `$`\mathcal{S}_{\text{intern}}`$ denote the deduplicated global symbol interner pool.

  Let $`\mathcal{S} = \{S_1, S_2, \dots, S_m\} \subset \mathcal{V}_{\text{AST}}`$` denote the finite set of `$`m`$ top-level architectural subsystems.
  Let $`\mathcal{M}_{\text{capabilities}} = \{c_1, c_2, \dots, c_n\} \subset \mathcal{V}_{\text{AST}}`$` denote the finite set of `$`n`$ SysML v2 `capability def` elements.
  Let $`\mathcal{E} = \{E_1, E_2, \dots, E_m\}`$ denote the set of projected Epic specifications.

  Each subsystem $`S_k \in \mathcal{S}`$ is formalized as a 6-tuple:

```math
  S_k = \langle \text{id}_{S_k}, \text{name}_{S_k}, \text{parts}(S_k), \text{ports}(S_k), \Delta_{S_k}, \text{span}_{S_k} \rangle
```

  where:

```math
  \begin{aligned}
  \text{id}_{S_k} &\in \mathbb{N}_{32} \quad (\text{contiguous arena handle}) \\
  \text{name}_{S_k} &\in \mathcal{S}_{\text{intern}} \quad (\text{interned subsystem symbol identifier}) \\
  \text{parts}(S_k) &\subset \mathcal{V}_{\text{AST}} \quad (\text{constituent structural child part definitions}) \\
  \text{ports}(S_k) &\subset \mathcal{V}_{\text{AST}} \quad (\text{boundary interface ports}) \\
  \Delta_{S_k} &\in \{0, 1\}^{128} \quad (\text{deterministic RFC 4122 UUIDv5 anchor}) \\
  \text{span}_{S_k} &= \langle \text{file\_id}, p_{\text{start}}, p_{\text{end}}, \text{line}, \text{col} \rangle \quad (\text{lexical source provenance})
  \end{aligned}
```

  Each capability $`c \in \mathcal{M}_{\text{capabilities}}`$ is formalized as a 6-tuple:

```math
  c = \langle \text{id}_c, \text{name}_c, \text{doc}_c, \text{owner}(c), \Delta_c, \text{span}_c \rangle
```

  where:

```math
  \begin{aligned}
  \text{id}_c &\in \mathbb{N}_{32} \quad (\text{contiguous arena handle}) \\
  \text{name}_c &\in \mathcal{S}_{\text{intern}} \quad (\text{interned capability symbol identifier}) \\
  \text{doc}_c &\in \mathcal{S}_{\text{intern}} \quad (\text{interned capability objective or description string}) \\
  \text{owner}(c) &\in \mathcal{S} \cup \{\bot\} \quad (\text{allocated owning subsystem handle or unassigned sentinel}) \\
  \Delta_c &\in \{0, 1\}^{128} \quad (\text{deterministic RFC 4122 UUIDv5 anchor}) \\
  \text{span}_c &= \langle \text{file\_id}, p_{\text{start}}, p_{\text{end}}, \text{line}, \text{col} \rangle \quad (\text{lexical source provenance})
  \end{aligned}
```

  The capability allocation function:

```math
  \text{Alloc} : \mathcal{M}_{\text{capabilities}} \to \mathcal{S}
```

  maps each capability to its owning subsystem.
  For each Epic $`E_k`$` (`$`k \in \{1, \dots, m\}`$):

```math
  E_k = \{ c \in \mathcal{M}_{\text{capabilities}} \mid \text{Alloc}(c) = S_k \}
```

  The capability allocation row mapping for each $`c \in E_k`$:

```math
  \text{Allocation}(c) = \langle \text{CapabilityName}(c), \text{SubsystemPackage}(\text{Alloc}(c)), \text{DescriptionObjective}(c) \rangle
```

  1. Exact Partition Completeness Invariant:
  The collection of capability sets $`\{E_1, \dots, E_m\}`$ covers the entire capability universe:

```math
  \bigcup_{k=1}^m E_k = \mathcal{M}_{\text{capabilities}}
```

```math
  \forall c \in \mathcal{M}_{\text{capabilities}}, \quad \text{Alloc}(c) \ne \bot \quad \wedge \quad \text{Alloc}(c) \in \mathcal{S}
```

  2. Exact Partition Disjointness Invariant:
  Distinct Epics contain strictly disjoint capability sets:

```math
  \forall i, j \in \{1, \dots, m\}, \quad i \ne j \implies E_i \cap E_j = \emptyset
```

```math
  \forall c \in \mathcal{M}_{\text{capabilities}}, \quad |\{ k \in \{1, \dots, m\} \mid c \in E_k \}| = 1
```

  3. Lexicographical Epic Indexing Invariant:
  The set of Epics is indexed strictly by canonical lexicographical symbol ordering:

```math
  S_a \prec_{\text{lex}} S_b \iff \text{Index}(E_a) \lt \text{Index}(E_b)
```

  4. Epic Document Representation Formalization:
  Each projected Epic document $`\mathcal{D}_{\text{Epic}}(S_k)`$ is formalized as a 6-tuple:

```math
  \mathcal{D}_{\text{Epic}}(S_k) = \langle \Delta_{E_k}, \text{name}_{S_k}, \text{Hierarchy}(S_k), \mathbf{T}_{\text{alloc}}(S_k), \mathbf{I}_{\text{boundary}}(S_k), \text{digest}_{E_k} \rangle
```

  where:

```math
  \begin{aligned}
  \Delta_{E_k} &\in \{0, 1\}^{128} \quad (\text{deterministic RFC 4122 UUIDv5 frontmatter anchor}) \\
  \text{name}_{S_k} &\in \mathcal{S}_{\text{intern}} \quad (\text{subsystem fully qualified name}) \\
  \text{Hierarchy}(S_k) &\subset \mathcal{V}_{\text{AST}} \quad (\text{structural decomposition tree of child parts and ports}) \\
  \mathbf{T}_{\text{alloc}}(S_k) &= [ \text{Allocation}(c) \mid c \in E_k ] \quad (\text{capability allocation roster sorted by } \prec_{\text{lex}}) \\
  \mathbf{I}_{\text{boundary}}(S_k) &\subset \mathcal{V}_{\text{AST}} \quad (\text{Level 1C boundary interface cross-references}) \\
  \text{digest}_{E_k} &\in \{0, 1\}^{256} \quad (\text{cryptographic content hash digest})
  \end{aligned}
```

  5. Deterministic Diagnostic Trigger Rules (REQ-0191):

```math
  \begin{aligned}
  \exists c \in \mathcal{M}_{\text{capabilities}} : \text{Alloc}(c) = \bot &\implies \text{Diagnostic}(c, \text{DiagnosticCode::E0500}, \text{UnallocatedCapabilityViolation}) \in \mathcal{D}_{\text{sink}} \\
  \exists c \in \mathcal{M}_{\text{capabilities}} : \text{Alloc}(c) \notin \mathcal{S} &\implies \text{Diagnostic}(c, \text{DiagnosticCode::E0500}, \text{OrphanedSubsystemCapability}) \in \mathcal{D}_{\text{sink}} \\
  \exists c \in \mathcal{M}_{\text{capabilities}}, \exists i \ne j : c \in E_i \wedge c \in E_j &\implies \text{Diagnostic}(c, \text{DiagnosticCode::E0500}, \text{DuplicateCapabilityAllocation}) \in \mathcal{D}_{\text{sink}} \\
  \exists S_a, S_b \in \mathcal{S} : S_a \ne S_b \wedge \text{FQN}(S_a) = \text{FQN}(S_b) &\implies \text{Diagnostic}(S_b, \text{DiagnosticCode::E0500}, \text{EpicIdentifierCollision}) \in \mathcal{D}_{\text{sink}} \\
  |\mathcal{D}_{\text{sink}}| \ge C_{\text{max\_errors}} &\implies \exists D_{\text{term}} \in \mathcal{D}_{\text{sink}} : \text{code}(D_{\text{term}}) = \text{DiagnosticCode::E0199}
  \end{aligned}
```

  6. Deterministic RFC 4122 UUIDv5 Anchor Invariant (Directive 1):

```math
  \begin{aligned}
  \Delta_{E_k} &= \text{UUIDv5}(\text{OID}_{\text{DEAP}}, \text{FQN}(S_k) \mathbin{\Vert} \text{"::Epic"}) \\
  \Delta_{S_k} &= \text{UUIDv5}(\text{OID}_{\text{DEAP}}, \text{FQN}(S_k)) \\
  \Delta_c &= \text{UUIDv5}(\text{OID}_{\text{DEAP}}, \text{FQN}(c)) \\
  \Delta_{\text{alloc}(c)} &= \text{UUIDv5}(\text{OID}_{\text{DEAP}}, \text{FQN}(S_k) \mathbin{\Vert} \text{"::Alloc::"} \mathbin{\Vert} \text{FQN}(c))
  \end{aligned}
```

  7. Streaming Artifact Sink Memory Invariant (REQ-0162, REQ-0177):

```math
  M_{\text{resident}}(\text{Emitter}) \le O(1) \quad \left(\text{independent of aggregate emitted bytes } \sum |\mathcal{D}_{\text{Epic}}|\right)
```

#### 3. Computational Complexity & Algorithmic Bounds

Epics Projection: Structural Decomposition & Subsystem Capability Mapping resides strictly in **Complexity Class P** (Deterministic Polynomial Time), executing in strictly deterministic linear time $`O(|C| + |S| + |A|)`$`, where `$`|C| = |\mathcal{M}_{\text{capabilities}}|`$` denotes the number of capability definitions, `$`|S| = |\mathcal{S}|`$` denotes the number of architectural subsystems, and `$`|A|`$ denotes the number of explicit allocation relationships.

  **Mathematical Delineation from the 8 NP Frontiers**:
  - *Delineation from NP-1 (REQ-0117)*: NP-1 addresses qualitative temporal interval algebra path consistency and difference logic SMT solving in $`O(N^3)`$ polynomial time. In contrast, REQ-0161 partitions static structural AST namespaces along established package boundaries without solving temporal interval constraints.
  - *Delineation from NP-2 (REQ-0147)*: NP-2 addresses structural allocation, interconnect clustering, and logical channel multiplexing via strongly NP-hard vector bin packing. In contrast, REQ-0161 downstream epic projection traverses resolved AST containment and explicit allocation relationships, synthesizing partition tables in deterministic linear time $`O(|C| + |S|)`$ without combinatorial bin-packing search or optimization heuristics.
  - *Delineation from NP-3 (REQ-0061--REQ-0063)*: NP-3 resolves subtyping lattices and multiple inheritance hierarchies via monotonic C3 linearization in $`O(V + E)`$ time. In contrast, REQ-0161 maps already-typed and instantiated capability definitions to their designated subsystem packages.
  - *Delineation from NP-4 (REQ-0135)*: NP-4 minimizes STPA hazard cut-sets and Unsafe Control Actions via NP-complete Minimal Hitting Set reductions. In contrast, REQ-0161 projects functional capability rosters to subsystem boundaries via direct relational projection.
  - *Delineation from NP-5 (REQ-0124)*: NP-5 addresses orthogonal discrete state machine reachability, deadlock, and livelock (PSPACE-complete / NP-complete under bounded model checking). In contrast, REQ-0161 synthesizes static epic specification documents without exploring state-space trajectories.
  - *Delineation from NP-6 (REQ-0105)*: NP-6 solves switched conservative flow networks via linear complementarity problems and Lemke pivoting (NP-complete). In contrast, REQ-0161 performs structural decomposition of AST package nodes without dynamic continuous equations.
  - *Delineation from NP-7 (REQ-0180)*: NP-7 performs register allocation and basic block scheduling in LUMI IR using Chaitin graph coloring (NP-complete). In contrast, REQ-0161 operates at the architecture specification layer prior to intermediate representation lowering.
  - *Delineation from NP-8 (REQ-0197)*: NP-8 proves the satisfiability of first-order invariant contracts via DPLL(T) SMT solvers. In contrast, REQ-0161 performs closed-form relational table synthesis.

  **Asymptotic Complexity Analysis**:
  Let $`|S| = |\mathcal{S}|`$` denote the number of architectural subsystems, `$`|C| = |\mathcal{M}_{\text{capabilities}}|`$` denote the number of capabilities, and `$`|A|`$ denote the number of explicit allocation relationships.
  1. *Subsystem Extraction & Canonical Lexicographical Sorting*:
     Extracting the $`m`$ top-level subsystem packages and sorting their fully qualified symbol names into canonical lexicographical order executes in deterministic time:

```math
T_{\text{sort}}(|S|) \in O(|S| \log |S|)
```

  2. *Capability Allocation Traversal & Hash/Array Resolution*:
     Traversing all $`|C|`$` capability definitions, resolving lexical parent scopes in `$`O(1)`$` operations via cached AST node handles (REQ-0035), and matching explicit allocation links `$`|A|`$ takes strictly linear time:

```math
T_{\text{resolve}}(|C|, |A|) \in O(|C| + |A|)
```

  3. *Exact Partition Verification (Completeness & Disjointness)*:
     Verifying that every capability belongs to exactly one subsystem Epic and that no capability is unallocated or duplicated executes via single-pass bit-vector or counter arrays in:

```math
T_{\text{verify}}(|C|, |S|) \in O(|C| + |S|)
```

  4. *Structural Decomposition Hierarchy Traversal*:
     Traversing child parts, internal subsystems, and boundary ports for each subsystem $`S_k`$ visits each AST node in the structural hierarchy exactly once:

```math
T_{\text{hierarchy}}(V_{\text{subsystem}}) \in O(V_{\text{subsystem}})
```

  5. *Streaming Markdown Tabular Emission*:
     Formatting and streaming the Subsystem Capability Allocation table and Epic document chunks directly through the streaming artifact sink interface executes in time proportional to document character length:

```math
T_{\text{stream}}(|C|, |S|) \in O(|C| + |S|)
```

  6. *Aggregate Worst-Case Execution Time*:
     Summing all constituent phases, the complete Epics projection pipeline executes within:

```math
T_{\text{total}}(|C|, |S|, |A|) \in O(|C| + |A| + |S| \log |S|)
```

     Since symbol interning provides pre-indexed qualified symbol identifiers, lexicographical sorting reduces to radix or direct index ordering, yielding linear time $`O(|C| + |S|)`$.
  7. *Parallel Work-Stealing Scaling (Directive 2)*:
     Independent subsystem Epics $`E_1, \dots, E_m`$` are partitioned and serialized across worker threads on a bounded work-stealing thread pool with worker bound `$`N_{\text{max\_workers}}`$:

```math
T_{\text{parallel}}(|C|, |S|, N_{\text{max\_workers}}) \in O\left( \frac{|C| + |S|}{N_{\text{max\_workers}}} + \log N_{\text{max\_workers}} \right)
```

  8. *Space Complexity & Arena Memory Bounds*:
     Subsystem rosters, capability descriptor records, and allocation bucket arrays reside in contiguous bump arena storage, requiring strictly $`O(|C| + |S|)`$` auxiliary space. The streaming artifact sink interface guarantees that resident document buffer memory remains strictly bounded by `$`O(1)`$` relative to total emitted artifact volume. The diagnostic error sink buffer is strictly bounded by `$`O(C_{\text{max\_errors}}) = O(1)`$ capacity.

#### 4. Verification & Conformance Criteria

Automated test suites shall deterministically verify compliance against synthetic abstract MBSE models (`Package_0`, `Package_1`, `Subsystem_0`, `Subsystem_1`, `Subsystem_Alpha`, `Subsystem_Beta`, `Capability_0`, `Capability_1`, `Capability_Alpha`, `Capability_Beta`, `Part_0`, `Port_0`, `param_x : Real`) across the following 16 verification gates:

  1. **Canonical Subsystem Partitioning Gate**: Ingest synthetic model `Package_0` declaring 3 top-level subsystems (`Subsystem_0`, `Subsystem_1`, `Subsystem_2`) and 9 capabilities partitioned evenly (3 capabilities per subsystem). Verify that the downstream projection engine synthesizes exactly 3 Epic specification documents, each containing its corresponding 3 allocated capabilities with zero diagnostics emitted.
  2. **Exact Capability Partition Completeness Gate**: Ingest a synthetic model declaring 100 capabilities across 5 subsystems. Verify that the union of capabilities across all 5 generated Epics equals the complete set $`\mathcal{M}_{\text{capabilities}}`$` (`$`\bigcup_{k=1}^5 E_k = \mathcal{M}_{\text{capabilities}}`$) without omission of a single capability node.
  3. **Disjoint Partition Verification Gate**: Verify that for all distinct Epic pairs $`E_i, E_j`$` (`$`i \ne j`$`), the intersection is strictly empty (`$`E_i \cap E_j = \emptyset`$), confirming that no capability is co-allocated to multiple primary Epics.
  4. **Unallocated Capability Rejection Gate (`E0500`)**: Ingest a synthetic model declaring an orphaned capability `Capability_Alpha` outside of any subsystem package and lacking an explicit allocation relationship. Assert deterministic compile-time rejection with diagnostic error code `E0500` (`UnallocatedCapabilityViolation`), reporting the source byte span of `Capability_Alpha`.
  5. **Orphaned Subsystem Capability Rejection Gate (`E0500`)**: Ingest a synthetic model where an explicit allocation relationship maps capability `Capability_Beta` to a non-existent subsystem `Subsystem_NonExistent`. Assert deterministic compile-time rejection with diagnostic error code `E0500` (`OrphanedSubsystemCapability`).
  6. **Duplicate / Conflicting Primary Allocation Rejection Gate (`E0500`)**: Ingest a synthetic model containing two explicit allocation statements mapping identical capability `Capability_0` to both `Subsystem_Alpha` and `Subsystem_Beta` without primary designation. Assert deterministic compile-time rejection with diagnostic error code `E0500` (`DuplicateCapabilityAllocation`).
  7. **Epic Qualified Identifier Collision Rejection Gate (`E0500`)**: Construct a synthetic test model where two distinct subsystem packages declare colliding qualified names resulting in identical Epic artifact targets. Assert deterministic compile-time rejection with diagnostic error code `E0500` (`EpicIdentifierCollision`).
  8. **Lexical Containment vs Explicit Allocation Precedence Gate**: Ingest a model where capability `Capability_0` is lexically defined inside `Package_Root::Subsystem_Alpha` but has an explicit allocation directive `allocate Capability_0 to Package_Root::Subsystem_Beta;`. Verify that the explicit allocation takes precedence and maps `Capability_0` into the Epic for `Subsystem_Beta` with zero diagnostics emitted.
  9. **Multi-Line Capability Objective Normalization Gate (REQ-0018)**: Ingest a capability containing multi-line doc comments with embedded line feeds (`\n`), Markdown pipe characters (`|`), and backticks. Verify that the emitted Subsystem Capability Allocation table normalizes multi-line text into a single escaped table cell without corrupting table column delimiters.
  10. **Hierarchical Subsystem Structural Decomposition Gate**: Ingest a subsystem containing nested child parts (`Part_0`, `Part_1`), internal sub-components, and directed ports (`Port_0`). Verify that the synthesized Epic document generates an indented structural decomposition tree reflecting complete component containment hierarchy.
  11. **Deterministic Qualified-Name Sorting Gate (REQ-0032)**: Ingest a model declaring subsystems and capabilities in random lexical order.
