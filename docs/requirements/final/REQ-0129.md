### REQ-0129: Upward Allocation Completeness Gate ($`\forall \text{Req}, \exists \text{Element}`$)

#### 1. Normative Statement

The safety compiler, formal verification engine, and traceability analysis pipeline of Subsystem 7 shall construct, validate, and verify the upward allocation completeness gate over the 7-tier bipartite traceability directed acyclic graph ($`G_{\text{trace}} = (V_{\text{trace}}, E_{\text{trace}})`$`) defined in REQ-0128. Specifically, the compiler shall enforce that every declared system requirement in the system requirement tier (`$`T_2`$`, denoted `$`\mathcal{R}_{\text{system}}`$`) allocates to at least one architectural element in the architectural classifier tier (`$`T_3`$`, denoted `$`\mathcal{C}_{\text{arch}}`$`), port and interface tier (`$`T_4`$`, denoted `$`\mathcal{I}_{\text{port}}`$`), or formal safety invariant tier (`$`T_5`$`, denoted `$`\mathcal{I}_{\text{safety}}`$).

  The upward allocation verification engine, AST lowered symbol resolver, and traceability gatekeeper shall strictly enforce the following structural, algebraic, and algorithmic invariants across all compilation units:
  1. **7-Tier Traceability Scope & Allocation Target Universe**:
     - The compiler shall partition the global traceability vertex set $`V_{\text{trace}}`$ into seven pairwise disjoint tiers:

```math
V_{\text{trace}} = T_1 \cup T_2 \cup T_3 \cup T_4 \cup T_5 \cup T_6 \cup T_7
```

       where $`T_1 = \mathcal{R}_{\text{mission}}`$` (Mission Requirements), `$`T_2 = \mathcal{R}_{\text{system}}`$` (System Requirements), `$`T_3 = \mathcal{C}_{\text{arch}}`$` (Architectural Classifiers: component definitions, part usages, action definitions, statecharts), `$`T_4 = \mathcal{I}_{\text{port}}`$` (Ports and Interfaces: directed ports, interface usages, interconnect channels), `$`T_5 = \mathcal{I}_{\text{safety}}`$` (Safety Invariants: formal state constraints, STPA safety invariants, assume-guarantee contracts), `$`T_6 = \mathcal{C}_{\text{code}}`$` (Realization Code: intermediate representation basic blocks, executable functions), and `$`T_7 = \mathcal{W}_{\text{verify}}`$ (Verification Witnesses: test benches, formal verification cases, analysis monitors).
     - The target allocation universe $`\mathcal{E}_{\text{target}}`$ for system requirements is defined as the union of architectural elements and formal safety invariants:

```math
\mathcal{E}_{\text{target}} = \mathcal{E}_{\text{architecture}} \cup \mathcal{I}_{\text{safety}} = (T_3 \cup T_4) \cup T_5
```

     - The requirement domain $`\mathcal{R}_{\text{system}}`$` and target allocation universe `$`\mathcal{E}_{\text{target}}`$ shall be strictly disjoint:

```math
\mathcal{R}_{\text{system}} \cap \mathcal{E}_{\text{target}} = \emptyset
```

  2. **Upward Allocation Completeness Gate Contract**:
     - For every declared system requirement $`r \in \mathcal{R}_{\text{system}}`$`, the upward allocation relation `$`E_{\text{alloc}} \subseteq E_{\text{trace}}`$` shall establish at least one directed allocation edge `$`(r, e) \in E_{\text{alloc}}`$` targeting an entity `$`e \in \mathcal{E}_{\text{target}}`$:

```math
\forall r \in \mathcal{R}_{\text{system}}, \quad \exists e \in \mathcal{E}_{\text{target}} \quad \text{such that } (r, e) \in E_{\text{alloc}}
```

     - The compiler shall compute the outgoing allocation set for each requirement:

```math
\text{Alloc}(r) = \{ e \in \mathcal{E}_{\text{target}} \mid (r, e) \in E_{\text{alloc}} \}
```

     - Any system requirement $`r \in \mathcal{R}_{\text{system}}`$` exhibiting an empty allocation set (`$`|\text{Alloc}(r)| = 0`$) constitutes an unallocated orphan requirement and shall be deterministically rejected at compile time with diagnostic error code `E0400` (`UnallocatedSystemRequirement`).
  3. **Strict 100% Allocation Coverage Metric Enforcement**:
     - The compiler shall evaluate the global upward allocation coverage ratio across all declared system requirements:

```math
\mu_{\text{alloc}}(\mathcal{R}_{\text{system}}) = \frac{|\{ r \in \mathcal{R}_{\text{system}} \mid |\text{Alloc}(r)| \ge 1 \}|}{|\mathcal{R}_{\text{system}}|}
```

     - The safety compilation gate shall strictly mandate $`\mu_{\text{alloc}}(\mathcal{R}_{\text{system}}) = 1.0`$` (100% coverage). If `$`|\mathcal{R}_{\text{system}}| \gt 0`$` and `$`\mu_{\text{alloc}}(\mathcal{R}_{\text{system}}) \lt 1.0`$, compilation shall fail deterministically, reporting each unallocated requirement node handle and its source file coordinates.
  4. **Hierarchical Requirement Decomposition & Leaf Completeness**:
     - System requirements may be hierarchically decomposed into sub-requirements via transitive decomposition relations ($`\prec_{\text{decomp}} \subset \mathcal{R}_{\text{system}} \times \mathcal{R}_{\text{system}}`$).
     - The compiler shall verify that for every composite requirement $`r_{\text{parent}} \in \mathcal{R}_{\text{system}}`$, either:
       * $`r_{\text{parent}}`$` defines an explicit direct allocation edge to an architectural element or safety invariant (`$`|\text{Alloc}(r_{\text{parent}})| \ge 1`$), or
       * Every constituent atomic leaf requirement $`r_{\text{leaf}} \in \text{Leaves}(r_{\text{parent}})`$` defines an explicit direct allocation edge (`$`|\text{Alloc}(r_{\text{leaf}})| \ge 1`$).
     - If a composite requirement is declared and any of its descendant leaf requirements lacks an allocation edge while the parent also lacks direct allocation, the compiler shall reject the model with diagnostic error code `E0400` (`UnallocatedSystemRequirement`), identifying the specific unallocated leaf node handles.
  5. **Admissibility of Allocation Target Classes**:
     - Every allocation edge $`(r, e) \in E_{\text{alloc}}`$` must terminate on a valid architectural classifier (`$`e \in T_3`$`), port or interface (`$`e \in T_4`$`), or formal safety invariant (`$`e \in T_5`$).
     - Any allocation statement targeting an element outside $`\mathcal{E}_{\text{target}}`$`--including allocations targeting uninstantiated packages, raw source prose, other un-decomposed requirements (`$`T_1, T_2`$`), or attempting to bypass architecture by targeting code blocks (`$`T_6`$`) or verification witnesses (`$`T_7`$) directly--shall be rejected at compile time with diagnostic error code `E0400` (`InvalidAllocationTarget`).
  6. **Reflexive and Cyclic Allocation Prohibition**:
     - Allocation edges must be strictly irreflexive: $`(r, r) \notin E_{\text{trace}}`$` for all `$`r \in \mathcal{R}_{\text{system}}`$. Any self-allocation declaration shall trigger diagnostic error code `E0400` (`ReflexiveAllocationDeclaration`).
     - Allocation chains and requirement decomposition graphs must be strictly acyclic. The compiler shall execute cycle detection on the combined allocation and decomposition digraph $`G_{\text{alloc}} = (V_{\text{trace}}, E_{\text{alloc}} \cup E_{\text{decomp}})`$`. Any cyclic dependency path (`$`v_1 \to v_2 \to \dots \to v_1`$) shall be rejected with diagnostic error code `E0400` (`CyclicAllocationDependency`).
  7. **Multi-Cardinality Allocation Topologies**:
     - The compiler shall support 1-to-N allocation mappings, where a single system requirement $`r`$ allocates to multiple architectural elements (e.g., allocating a functional requirement across two redundant classifiers `Classifier_Alpha` and `Classifier_Beta`, or across an interface `Port_1` and a safety invariant `Invariant_Safe_0`).
     - The compiler shall support N-to-1 allocation mappings, where multiple distinct system requirements $`r_1, r_2 \in \mathcal{R}_{\text{system}}`$` allocate to the same architectural element `$`e \in \mathcal{E}_{\text{target}}`$.
  8. **Architectural Directives Compliance**:
     - *Directive 1 (Deterministic UUIDv5 Anchors)*: Every requirement AST node, architectural element, safety invariant, and allocation edge $`(r, e)`$` shall be assigned an immutable deterministic RFC 4122 UUIDv5 identifier derived from the canonical DEAP compiler namespace OID and the fully qualified symbol path (`$`\text{UUIDv5}(\text{OID}_{\text{DEAP}}, \text{FQN}(r) \mathbin{\Vert} \text{\_allocates\_to\_} \mathbin{\Vert} \text{FQN}(e))`$) per REQ-0010.
     - *Directive 2 (Bounded Work-Stealing Parallelism)*: Parallel extraction of requirement sets, allocation edge validation, leaf completeness traversal, and coverage metric computation across decoupled packages shall execute strictly on a bounded work-stealing thread pool with worker bound $`N_{\text{max\_workers}}`$ per REQ-0012.
     - *Directive 3 (String Interner Allocation Exception)*: Interning requirement identifiers, element names, allocation rationales, and qualified path strings into the global symbol interner pool per REQ-0036 is the sole permitted exception to zero-copy memory management.
     - *Directive 4 (Synchronization Token Error Recovery)*: The safety compiler shall implement synchronization token error recovery on statement delimiters (`;`) and block boundaries (`}`). When semantic violations occur (`E0400`), diagnostics shall accumulate in the error sink buffer $`\mathcal{D}_{\text{sink}}`$`, substitute typed error sentinels (`$`\bot_{\text{alloc}}`$`), and continue validating subsequent requirement declarations. If accumulated diagnostics reach capacity `$`C_{\text{max\_errors}}`$, terminal diagnostic `E0199` shall be emitted and compilation halted gracefully per REQ-0013 and REQ-0016.
     - *Directive 5 (Panic-Free Release Isolation)*: The traceability verification pipeline shall strictly enforce a deterministic, non-panicking execution contract with total-function error handling. Verification latency ($`\lt 25\text{ ms}`$` for `$`10^4`$` requirements and allocation edges) and peak RSS memory (`$`\lt 100\text{ MB}`$) performance gates shall be evaluated exclusively in compiled Release mode (`--release`) under dedicated benchmark harnesses isolated from CI logic tests per REQ-0011 and REQ-0196.

  All diagnostic messages, test models, and illustrative examples shall strictly employ synthetic abstract MBSE placeholders (`Package_0`, `Package_1`, `Requirement_0`, `Requirement_1`, `Requirement_Leaf_0`, `Requirement_Leaf_1`, `Classifier_Alpha`, `Classifier_Beta`, `Part_Alpha`, `Part_Beta`, `Port_1`, `Port_2`, `Flow_A`, `Invariant_Safe_0`, `Invariant_Safe_1`, `Action_Alpha`, `param_x : Real`), strictly prohibiting hardcoded domain concepts, mock data, and non-ASCII dashes.

#### 2. Formal Invariant

Let $`\mathcal{V}_{\text{AST}}`$ denote the universe of allocated AST nodes in contiguous bump arena storage. The global 7-tier traceability graph is formalized as a directed acyclic multigraph:

```math
  G_{\text{trace}} = \langle V_{\text{trace}}, E_{\text{trace}} \rangle
```

  where the vertex universe $`V_{\text{trace}} \subset \mathcal{V}_{\text{AST}}`$ is partitioned into seven mutually disjoint subsets:

```math
  V_{\text{trace}} = \bigcup_{i=1}^7 T_i \quad \text{such that} \quad \forall j, k \in \{1, \dots, 7\}, \, j \ne k \implies T_j \cap T_k = \emptyset
```

  The seven constituent tiers are defined as:

```math
  \begin{aligned}
  T_1 &= \mathcal{R}_{\text{mission}} \quad (\text{Mission Requirements}) \\
  T_2 &= \mathcal{R}_{\text{system}} \quad (\text{System Requirements}) \\
  T_3 &= \mathcal{C}_{\text{arch}} \quad (\text{Architectural Classifiers: Parts, Subsystems, Actions, Statecharts}) \\
  T_4 &= \mathcal{I}_{\text{port}} \quad (\text{Ports, Interfaces, Interconnect Channels}) \\
  T_5 &= \mathcal{I}_{\text{safety}} \quad (\text{Formal Safety Invariants, Constraint Usages, Barrier Contracts}) \\
  T_6 &= \mathcal{C}_{\text{code}} \quad (\text{Realization Code, Executable Basic Blocks}) \\
  T_7 &= \mathcal{W}_{\text{verify}} \quad (\text{Verification Witnesses, Proof Obligations, Test Cases})
  \end{aligned}
```

  The target allocation universe $`\mathcal{E}_{\text{target}}`$ encompasses all architectural elements and formal safety invariants:

```math
  \mathcal{E}_{\text{target}} = \mathcal{E}_{\text{architecture}} \cup \mathcal{I}_{\text{safety}} = (T_3 \cup T_4) \cup T_5
```

  The upward allocation relation $`E_{\text{alloc}}`$ is defined as the set of directed edges from system requirements to architectural elements or safety invariants:

```math
  E_{\text{alloc}} \subseteq E_{\text{trace}} \cap \left( \mathcal{R}_{\text{system}} \times \mathcal{E}_{\text{target}} \right)
```

  For each system requirement $`r \in \mathcal{R}_{\text{system}}`$, the allocated target set and out-degree are given by:

```math
  \begin{aligned}
  \text{Alloc}(r) &= \{ e \in \mathcal{E}_{\text{target}} \mid (r, e) \in E_{\text{alloc}} \} \\
  \text{deg}^+_{\text{alloc}}(r) &= |\text{Alloc}(r)|
  \end{aligned}
```

  1. Upward Allocation Completeness Invariant:
     Every declared system requirement must allocate to at least one architectural element or formal safety invariant:

```math
  \forall r \in \mathcal{R}_{\text{system}}, \quad \exists e \in \mathcal{E}_{\text{architecture}} \cup \mathcal{I}_{\text{safety}} \quad \text{such that } (r, e) \in E_{\text{trace}}
```

  Equivalently:

```math
  \forall r \in \mathcal{R}_{\text{system}}, \quad |\text{Alloc}(r)| \ge 1
```

  2. Global Allocation Coverage Metric Invariant:
     The upward allocation coverage metric $`\mu_{\text{alloc}}(\mathcal{R}_{\text{system}})`$ must evaluate to unity:

```math
  \mu_{\text{alloc}}(\mathcal{R}_{\text{system}}) = \frac{|\{ r \in \mathcal{R}_{\text{system}} \mid |\text{Alloc}(r)| \ge 1 \}|}{|\mathcal{R}_{\text{system}}|} = 1.0
```

  The orphan requirement set $`\mathcal{R}_{\text{orphan}}`$ is defined as:

```math
  \mathcal{R}_{\text{orphan}} = \{ r \in \mathcal{R}_{\text{system}} \mid |\text{Alloc}(r)| = 0 \}
```

  Completeness holds if and only if $`\mathcal{R}_{\text{orphan}} = \emptyset`$:

```math
  \mathcal{R}_{\text{orphan}} = \emptyset \iff \mu_{\text{alloc}}(\mathcal{R}_{\text{system}}) = 1.0
```

  3. Hierarchical Decomposition Allocation Invariant:
     Let $`\prec_{\text{decomp}} \subset \mathcal{R}_{\text{system}} \times \mathcal{R}_{\text{system}}`$` denote the irreflexive requirement decomposition relation. Let `$`\text{Leaves}(r) \subseteq \mathcal{R}_{\text{system}}`$` denote the set of atomic leaf requirements reachable from `$`r`$:

```math
  \text{Leaves}(r) = \{ c \in \mathcal{R}_{\text{system}} \mid c \prec_{\text{decomp}}^* r \land \neg \exists k \in \mathcal{R}_{\text{system}} : k \prec_{\text{decomp}} c \}
```

  For every composite requirement $`r \in \mathcal{R}_{\text{system}}`$:

```math
  (|\text{Alloc}(r)| \ge 1) \lor \left( \forall c \in \text{Leaves}(r), \, |\text{Alloc}(c)| \ge 1 \right)
```

  4. Allocation Target Class Validity Invariant:
     No allocation edge may target an entity outside $`\mathcal{E}_{\text{target}}`$:

```math
  \forall (r, e) \in E_{\text{alloc}}, \quad e \in (T_3 \cup T_4 \cup T_5)
```

  5. Irreflexivity and Acyclicity Invariants:
     No system requirement may allocate to itself, and the combined allocation and decomposition digraph must remain acyclic:

```math
  \begin{aligned}
  \forall r &\in \mathcal{R}_{\text{system}}, \quad (r, r) \notin E_{\text{trace}} \\
  \forall k &\ge 1, \quad \neg \exists (v_0, v_1, \dots, v_k) \text{ such that } (v_i, v_{i+1}) \in (E_{\text{alloc}} \cup E_{\text{decomp}}) \land v_k = v_0
  \end{aligned}
```

  6. Deterministic Diagnostic Trigger Rules (REQ-0191):

```math
  \begin{aligned}
  \exists r \in \mathcal{R}_{\text{system}} : |\text{Alloc}(r)| = 0 &\implies \text{Diagnostic}(r, \text{DiagnosticCode::E0400}, \text{UnallocatedSystemRequirement}) \in \mathcal{D}_{\text{sink}} \\
  \exists (r, e) \in E_{\text{alloc}} : e \notin \mathcal{E}_{\text{target}} &\implies \text{Diagnostic}((r, e), \text{DiagnosticCode::E0400}, \text{InvalidAllocationTarget}) \in \mathcal{D}_{\text{sink}} \\
  \exists r \in \mathcal{R}_{\text{system}} : (r, r) \in E_{\text{trace}} &\implies \text{Diagnostic}(r, \text{DiagnosticCode::E0400}, \text{ReflexiveAllocationDeclaration}) \in \mathcal{D}_{\text{sink}} \\
  \exists C \subset (E_{\text{alloc}} \cup E_{\text{decomp}}) : \text{IsCycle}(C) &\implies \text{Diagnostic}(\text{head}(C), \text{DiagnosticCode::E0400}, \text{CyclicAllocationDependency}) \in \mathcal{D}_{\text{sink}} \\
  |\mathcal{D}_{\text{sink}}| \ge C_{\text{max\_errors}} &\implies \exists D_{\text{term}} \in \mathcal{D}_{\text{sink}} : \text{code}(D_{\text{term}}) = \text{DiagnosticCode::E0199}
  \end{aligned}
```

  7. Deterministic RFC 4122 UUIDv5 Anchor Invariant (Directive 1):

```math
  \begin{aligned}
  \forall r \in \mathcal{R}_{\text{system}}, &\quad \Delta_r = \text{UUIDv5}(\text{OID}_{\text{DEAP}}, \text{FQN}(r)) \\
  \forall e \in \mathcal{E}_{\text{target}}, &\quad \Delta_e = \text{UUIDv5}(\text{OID}_{\text{DEAP}}, \text{FQN}(e)) \\
  \forall a = (r, e) \in E_{\text{alloc}}, &\quad \Delta_a = \text{UUIDv5}(\text{OID}_{\text{DEAP}}, \text{FQN}(r) \mathbin{\Vert} \text{\_allocates\_to\_} \mathbin{\Vert} \text{FQN}(e))
  \end{aligned}
```

#### 3. Computational Complexity & Algorithmic Bounds

Upward allocation completeness verification, target validity checking, decomposition hierarchy traversal, and coverage metric computation reside in **Complexity Class P** (Deterministic Polynomial Time).

  **Mathematical Delineation from Algorithmic Frontiers NP-1, NP-2, NP-4, and NP-8**:
  - *Delineation from NP-4 (STPA Minimal Hazard Cut-Sets & UCA Minimization, REQ-0135)*: Computing minimal hazard cut-sets and minimal hitting sets over unsafe control action hypergraphs is NP-complete, requiring bounded branch-and-bound or greedy logarithmic approximation. In contrast, upward allocation completeness checking does not search for minimal hitting sets or optimal combinatorial covers; it evaluates static 1-to-N adjacency degrees over an explicitly declared bipartite graph.
  - *Delineation from NP-2 (Structural Allocation & Vector Bin Packing, REQ-0147)*: Algorithmic Bound NP-2 addresses the strongly NP-hard problem of multi-dimensional resource bin packing when placing unassigned logical functions onto physical processors with multi-capacity constraints. In contrast, REQ-0129 verifies whether declared allocation edges exist in the AST model; it does not solve an optimization or placement problem.
  - *Delineation from NP-1 (Temporal Consistency, REQ-0117) and NP-8 (SMT Proof Obligations, REQ-0197)*: Upward allocation verification involves zero first-order SMT solver calls, zero quantifier elimination, and zero interval constraint propagation. All checks execute via direct graph traversal and bitset operations in deterministic polynomial time.

  **Asymptotic Complexity Analysis**:
  Let $`V_R = |\mathcal{R}_{\text{system}}|`$` denote the number of system requirements, `$`V_E = |\mathcal{E}_{\text{target}}|`$` denote the number of candidate architectural and safety elements, `$`V = |V_{\text{trace}}|`$` denote the total number of traceability vertices (`$`V = \sum_{i=1}^7 |T_i|`$`), and `$`E = |E_{\text{trace}}|`$` denote the total number of traceability edges, with `$`E_{\text{alloc}} = |E_{\text{alloc}}|`$` denoting the number of upward allocation edges. Let `$`h_{\text{decomp}}`$` denote the maximum depth of the requirement decomposition hierarchy (`$`h_{\text{decomp}} \le 16 \ll V`$).
  1. *Traceability Adjacency List Construction*:
     Lowering AST allocation statements and partitioning vertices into tiers $`T_1`$` through `$`T_7`$ requires traversing the bump arena AST nodes and inserting directed adjacency records. This indexing pass takes:

```math
     T_{\text{index}}(V, E) \in O(V + E)
```

  2. *Allocation Out-Degree Verification*:
     For each system requirement $`r \in \mathcal{R}_{\text{system}}`$`, the compiler performs an `$`O(1)`$` amortized lookup in the adjacency list to verify `$`|\text{Alloc}(r)| \ge 1`$. Across all system requirements:

```math
     T_{\text{degree}}(V_R) \in O(V_R)
```

  3. *Allocation Target Class Conformance Checking*:
     For each allocation edge $`(r, e) \in E_{\text{alloc}}`$`, the engine checks whether the target element's tier bitmask satisfies `$`e \in (T_3 \cup T_4 \cup T_5)`$`. Each bitmask inspection requires `$`O(1)`$ operations:

```math
     T_{\text{target}}(E_{\text{alloc}}) \in O(E_{\text{alloc}})
```

  4. *Hierarchical Decomposition Completeness Traversal*:
     For composite requirements relying on leaf completeness, traversing the decomposition hierarchy down to leaves takes time proportional to the decomposition sub-forest $`(V_{\text{decomp}}, E_{\text{decomp}})`$. Using depth-first search (DFS) with memoization:

```math
     T_{\text{decomp}}(V_R, E_{\text{decomp}}) \in O(V_R + E_{\text{decomp}})
```

  5. *Acyclicity & Cycle Detection*:
     Verifying that $`G_{\text{alloc}} = (V_{\text{trace}}, E_{\text{alloc}} \cup E_{\text{decomp}})`$ contains no directed cycles executes via Tarjan's strongly connected components (SCC) algorithm or Kahn's topological sort:

```math
     T_{\text{cycle}}(V, E) \in O(V + E)
```

  6. *Global Coverage Metric Evaluation*:
     Counting the cardinality of allocated requirements and dividing by $`V_R`$ requires a single linear pass over the requirement bitset:

```math
     T_{\text{coverage}}(V_R) \in O(V_R)
```

  7. *Aggregate Worst-Case Time Complexity*:
     Combining all verification passes, total compile-time execution time is bounded by:

```math
     T_{\text{total}}(V, E) \in O(V + E)
```

     Execution is strictly linear in the total size of the traceability graph, operating deterministically without backtracking or combinatorial explosion.
  8. *Parallel Work-Stealing Scaling (Directive 2)*:
     When verifying $`P`$` independent packages or decoupled subsystem requirement trees across `$`N_{\text{max\_workers}}`$ threads on a bounded work-stealing thread pool:

```math
     T_{\text{parallel}}(V, E, N_{\text{max\_workers}}) \in O\left( \frac{V + E}{N_{\text{max\_workers}}} + \log N_{\text{max\_workers}} \right)
```

  9. *Space Complexity & Arena Memory Bounds*:
     All requirement vertices, target element handles, and allocation edges reside in contiguous bump arena storage, requiring $`O(V + E)`$` bytes. The bitset indices for orphan tracking require `$`O(V_R / 64)`$` 64-bit words (`$`O(V)`$` auxiliary memory). The diagnostic error sink buffer is strictly bounded by `$`O(C_{\text{max\_errors}}) = O(1)`$ capacity.

#### 4. Verification & Conformance Criteria

Automated test suites shall deterministically verify compliance against synthetic abstract MBSE models (`Package_0`, `Package_1`, `Requirement_0`, `Requirement_1`, `Requirement_Leaf_0`, `Requirement_Leaf_1`, `Classifier_Alpha`, `Classifier_Beta`, `Part_Alpha`, `Part_Beta`, `Port_1`, `Port_2`, `Flow_A`, `Invariant_Safe_0`, `Invariant_Safe_1`, `Action_Alpha`, `param_x : Real`) across the following 17 verification gates:

  1. **Canonical Direct Requirement-to-Classifier Allocation Gate**: Ingest synthetic model `Package_0` declaring system requirement `Requirement_0` and architectural classifier `Classifier_Alpha` (`part def Classifier_Alpha`). Declare an explicit allocation `allocate Requirement_0 to Classifier_Alpha;`. Verify that the compiler records the allocation edge $`( \text{Requirement\_0}, \text{Classifier\_Alpha} ) \in E_{\text{alloc}}`$`, evaluates coverage `$`\mu_{\text{alloc}} = 1.0`$, and completes compilation with zero diagnostics emitted.
  2. **Direct Requirement-to-Port Allocation Gate**: Ingest synthetic model `Package_0` declaring system requirement `Requirement_0` and directed port `Port_1` (`port def Port_1`). Declare allocation `allocate Requirement_0 to Port_1;`. Verify that the compiler validates `Port_1` as a member of tier $`T_4 \subset \mathcal{E}_{\text{target}}`$, accepts the allocation edge, and completes with zero diagnostics emitted.
  3. **Direct Requirement-to-Safety-Invariant Allocation Gate**: Ingest synthetic model `Package_0` declaring system requirement `Requirement_0` and formal safety invariant `Invariant_Safe_0` (`assert constraint Invariant_Safe_0`). Declare allocation `allocate Requirement_0 to Invariant_Safe_0;`. Verify that the compiler validates `Invariant_Safe_0` as a member of tier $`T_5 \subset \mathcal{E}_{\text{target}}`$, confirms complete allocation, and emits zero diagnostics.
  4. **Multi-Target Redundant Allocation Gate (1-to-N Mapping)**: Ingest synthetic model `Package_0` declaring requirement `Requirement_0` allocated to three distinct targets: classifier `Classifier_Alpha` ($`T_3`$), directed port `Port_1` ($`T_4`$), and safety invariant `Invariant_Safe_0` ($`T_5`$`). Verify that all three allocation edges are recorded in `$`E_{\text{alloc}}`$`, `$`|\text{Alloc}(\text{Requirement\_0})| = 3`$, and the model passes validation with zero diagnostics.
  5. **Multi-Requirement Shared Architecture Allocation Gate (N-to-1 Mapping)**: Ingest synthetic model `Package_0` declaring three distinct system requirements `Requirement_0`, `Requirement_1`, and `Requirement_2`, each allocating to the same architectural classifier `Classifier_Alpha`. Verify that $`|\text{Alloc}(r_i)| = 1`$` for all three requirements, global coverage is `$`\mu_{\text{alloc}} = 1.0`$, and zero diagnostics are emitted.
  6. **Missing Requirement Allocation Compile-Time Rejection Gate (`E0400`)**: Ingest synthetic model `Package_0` declaring system requirement `Requirement_0` with zero declared allocation statements. Verify that the compiler detects $`|\text{Alloc}(\text{Requirement\_0})| = 0`$, deterministically rejects the compilation unit, and emits diagnostic error code `E0400` (`UnallocatedSystemRequirement`) reporting the exact source span of `Requirement_0`.
  7. **Partial Allocation Coverage Metric Failure Gate (`E0400`)**: Ingest synthetic model `Package_0` declaring ten system requirements `Requirement_0` through `Requirement_9`. Declare valid allocation statements for `Requirement_0` through `Requirement_8`, but omit allocation for `Requirement_9`. Verify that the compiler computes coverage $`\mu_{\text{alloc}} = 9/10 = 0.9 \lt 1.0`$, rejects compilation, and emits diagnostic error code `E0400` (`UnallocatedSystemRequirement`) identifying `Requirement_9`.
  8. **Invalid Allocation Target Rejection Gate (`E0400`)**: Ingest synthetic model `Package_0` declaring system requirement `Requirement_0` and attempting to allocate to uninstantiated package container `Package_1` (`allocate Requirement_0 to Package_1;`). Verify that the compiler verifies that `Package_1` $`\notin \mathcal{E}_{\text{target}}`$, deterministically rejects the declaration, and emits diagnostic error code `E0400` (`InvalidAllocationTarget`).
