### REQ-0087: SysML v2 VerificationCaseDefinition (`verification def`) & VerificationUsage

#### 1. Normative Statement

The KerML/SysML v2 metamodel lowering engine and semantic type checker shall formalize `verification def` (VerificationCaseDefinition) and `verification` (VerificationCaseUsage / VerificationUsage) AST elements as strongly typed behavioral verification procedures specializing KerML `Behavior`, executing formal test, analysis, inspection, or demonstration methods against subject models to emit formal tri-state verification verdicts.

  The lowering engine shall strictly verify and enforce the following structural, semantic, and typing invariants during verification case lowering:
  1. **Dual Inheritance Specialization & Metamodel Classification**: In the KerML/SysML v2 classifier hierarchy, `VerificationCaseDefinition` shall specialize KerML `Behavior` (and SysML v2 `CaseDefinition`, which specializes KerML `CalculationDefinition` and KerML `Behavior`), inheriting occurrence lifecycle semantics, temporal execution intervals, and classifier feature ownership. Every `VerificationUsage` shall specialize KerML `Step` and KerML `OccurrenceUsage` (as well as SysML v2 `CaseUsage`), representing the discrete executable invocation or contextual instantiation of a verification case within an enclosing classifier definition (such as `part def`, `action def`, or `verification def`) or package.
  2. **Subject Parameter Declaration & Directionality Invariants**: Every `VerificationCaseDefinition` shall declare at least one formal subject parameter feature $`s_{\text{formal}} \in \mathbf{P}_{\text{subj}}`$`, denoting the system element, component, or item under verification. The subject parameter must declare or default to an input directionality (`$`\text{dir}(s_{\text{formal}}) \in \{ \text{In}, \text{InOut} \}`$). Declaring a subject parameter with `Out` directionality ($`\text{dir}(s_{\text{formal}}) = \text{Out}`$) shall be strictly rejected at compile time with diagnostic error code `E0201` in accordance with REQ-0191.
  3. **Subject Parameter Binding & Subtyping Conformance**: Every `VerificationUsage` $`VU`$` shall bind its formal subject parameter to a concrete subject instance, part usage, or port expression (`$`s_{\text{actual}}`$) accessible within its lexical featuring scope. The semantic type checker shall statically verify that:
     - The actual subject argument $`s_{\text{actual}}`$` is provided for every required formal subject parameter (`$`\mathbf{A}_{\text{subj}} \ne \emptyset`$). Any missing subject binding shall trigger diagnostic error code `E0200`.
     - The evaluated classifier type of the actual subject argument $`\tau(s_{\text{actual}})`$` must specialize or equal the declared type of the formal subject parameter `$`\tau(s_{\text{formal}})`$` within the subtyping meet-semilattice (`$`\tau(s_{\text{actual}}) \le_{\text{sub}} \tau(s_{\text{formal}})`$). Passing an incompatible subject type shall be strictly rejected at compile time with diagnostic error code `E0202`.
     - The actual subject expression must be read-accessible in the verification context. Passing uninitialized features or write-only ports shall trigger diagnostic error code `E0201`.
  4. **Formal Tri-State Verification Verdict Codomain**: Every `VerificationCaseDefinition` and `VerificationUsage` shall yield a formal verification verdict $`\nu \in \mathcal{V}`$`, where `$`\mathcal{V}`$` is the canonical tri-state verdict space `$`\mathcal{V} = \{ \text{Pass}, \text{Fail}, \text{Inconclusive} \}`$. The verification definition shall declare a mandatory result parameter (`verdict : VerdictKind`, where `VerdictKind` represents the canonical tri-state enumeration) or return an expression whose codomain unifies with $`\mathcal{V}`$. Declaring a verification case lacking a valid verdict return type or yielding a non-verdict type shall be rejected at compile time with diagnostic error code `E0200`.
  5. **Verification Method Kinds**: A `VerificationCaseDefinition` may declare an explicit verification method kind $`\kappa_{\text{method}} \in \{ \text{Test}, \text{Analysis}, \text{Inspection}, \text{Demonstration} \}`$. In accordance with pure schema-driven compilation, the method kind specifies the analytical, formal, or empirical verification protocol governing the behavioral step execution without hardcoded domain assumptions.
  6. **Traceability Binding to Requirements (`verify requirement`)**: The lowering engine shall formalize the SysML v2 `verify` relationship (syntax `verify requirement <Req>` or `verify <RequirementUsage>`), creating a directed traceability edge from verification case $`V`$` to requirement `$`R`$` (`$`V \xrightarrow{\text{verifies}} R`$). The compiler and verification engine shall enforce the formal certification gate:
     - Requirement $`R`$` is certified as formally verified for subject instance `$`s`$ if and only if the verification case evaluates to `Pass`: $`\text{Verified}(R, s) \iff (\text{eval}(V, s) \equiv \text{Pass})`$.
     - If $`\text{eval}(V, s) \equiv \text{Fail}`$, the requirement is certified as refuted / violated.
     - If $`\text{eval}(V, s) \equiv \text{Inconclusive}`$, the verification procedure failed to resolve requirement satisfaction, preventing certification.
     - Any dangling or unresolvable requirement reference in a `verify` relationship shall be rejected at compile time with diagnostic error code `E0200`.
  7. **Behavioral Step Execution & Assertion Semantics**: As a specialization of KerML `Behavior`, a `VerificationCaseDefinition` may contain an ordered workflow of execution steps, setup actions, assertions (`assert constraint`), measurements, evaluations, and teardown steps. An assertion failure during verification execution shall deterministically force the evaluation verdict from `Pass` to `Fail`.
  8. **Verification Call Graph Acyclicity**: The lowering engine shall construct a directed dependency graph $`\mathcal{G}_{\text{v\_dep}} = (\mathcal{VD}, \mathcal{E}_{\text{v\_dep}})`$` tracking invocations between verification cases. Cyclic invocations (`$`VD_1 \to^+ VD_1`$) shall be strictly prohibited and detected via topological cycle detection, emitting diagnostic error code `E0203`.

  **Architectural Directives Compliance**:
  - *Directive 1 (Deterministic UUIDv5 Anchors)*: Every lowered `VerificationCaseDefinition`, `VerificationUsage`, `SubjectParameter`, `VerdictParameter`, and `VerifyRelationship` AST node shall be assigned a deterministic RFC 4122 UUIDv5 identifier generated by namespace-hashing the fully qualified symbol path (e.g., `Package_0::VerificationDef_Alpha`) with the canonical compiler namespace OID per REQ-0010.
  - *Directive 2 (Bounded Work-Stealing Parallelism)*: Parallel lowering, semantic type checking, and independent test dispatch of verification cases across distinct compilation units shall execute strictly on a bounded work-stealing thread pool with worker bound $`N_{\text{max\_workers}}`$ per REQ-0012.
  - *Directive 3 (String Interner Allocation Exception)*: Scalar identifiers, verification case names, parameter names, and qualified path tokens shall be interned into the global deduplicated symbol interner pool per REQ-0036 as the sole permitted exception to zero-copy memory management.
  - *Directive 4 (Synchronization Token Error Recovery)*: The lowering engine shall implement synchronization token error recovery per REQ-0013 and REQ-0016 on declaration and boundary delimiters. Upon encountering any diagnostic defect (`E0200`, `E0201`, `E0202`, `E0203`), the engine records the diagnostic into preallocated error sink $`\mathcal{D}_{\text{sink}}`$`, assigns error sentinel node `$`\bot_{\text{verif}}`$` or `$`\bot_{\text{type}}`$`, and resynchronizes without aborting compilation. If accumulated diagnostics reach capacity `$`C_{\text{max\_errors}}`$, the compiler shall emit terminal diagnostic `E0199` and halt gracefully.
  - *Directive 5 (Panic-Free Release Isolation)*: Production compiler library code and verification dispatch runtime shall enforce a deterministic, non-panicking execution contract with total-function termination across all inputs. Performance latency ($`\lt 25\text{ ms}`$`) and peak memory RSS (`$`\lt 100\text{ MB}`$` for `$`10^5`$ verification nodes) performance gates shall be evaluated exclusively in compiled Release mode (`--release`) under dedicated benchmark harnesses isolated from CI logic tests per REQ-0011 and REQ-0196.

  All diagnostic messages, test models, and illustrative examples shall strictly employ synthetic abstract MBSE placeholders (`Package_0`, `Classifier_Alpha`, `Classifier_Beta`, `VerificationDef_Alpha`, `VerificationDef_Beta`, `VerificationUsage_1`, `VerificationUsage_2`, `Requirement_1`, `Requirement_2`, `param_x : Real`, `param_y : Real`, `verdict_val : VerdictKind`), strictly prohibiting hardcoded domain concepts, mock data, and non-ASCII dashes.

#### 2. Formal Invariant

Let $`\mathcal{V}_{\text{AST}}`$` denote the universe of allocated AST nodes in contiguous bump arena storage. Let `$`\mathcal{VD} \subset \mathcal{V}_{\text{AST}}`$` denote the set of verification case definition nodes, let `$`\mathcal{VU} \subset \mathcal{V}_{\text{AST}}`$` denote the set of verification usage nodes, and let `$`\mathcal{RD} \subset \mathcal{V}_{\text{AST}}`$ denote the set of requirement nodes.

  Let $`\mathcal{V}`$ denote the canonical tri-state verification verdict space:

```math
\mathcal{V} = \{ \text{Pass}, \text{Fail}, \text{Inconclusive} \}
```

  Let $`\mathcal{M}_{\text{method}}`$ denote the universe of formal verification methods:

```math
\mathcal{M}_{\text{method}} = \{ \text{Test}, \text{Analysis}, \text{Inspection}, \text{Demonstration} \}
```

  The metamodel subtyping posets for verification case definitions and usages are formalized as:

```math
\text{VerificationDef} \le_{\text{sub}} \text{CaseDefinition} \le_{\text{sub}} \text{Behavior} \le_{\text{sub}} \text{Class}
```

```math
\text{VerificationUsage} \le_{\text{sub}} \text{CaseUsage} \le_{\text{sub}} \text{Step} \le_{\text{sub}} \text{OccurrenceUsage} \le_{\text{sub}} \text{Feature}
```

  Each verification case definition $`VD \in \mathcal{VD}`$ is formalized as a 9-tuple:

```math
VD = \langle \text{id}_{VD}, \text{name}_{VD}, \text{owner}_{VD}, \kappa_{\text{method}}, \mathbf{P}_{\text{subj}}, \mathbf{P}_{\text{param}}, p_{\text{verdict}}, \Delta_{VD}, \text{span}_{VD} \rangle
```

  where:

```math
\begin{aligned}
\text{id}_{VD} &\in \mathbb{N}_{32} \quad (\text{contiguous arena node handle}) \\
\text{name}_{VD} &\in \mathcal{S}_{\text{intern}} \quad (\text{interned symbol identifier}) \\
\text{owner}_{VD} &\in \mathcal{C} \cup \mathcal{P}_{\text{pkg}} \quad (\text{owning classifier or package}) \\
\kappa_{\text{method}} &\in \mathcal{M}_{\text{method}} \quad (\text{declared verification method kind}) \\
\mathbf{P}_{\text{subj}} &= (s_1, \dots, s_j) \in \mathcal{P}_{\text{param}}^j \quad (\text{non-empty vector of formal subject parameters, } j \ge 1) \\
\mathbf{P}_{\text{param}} &= (p_1, \dots, p_k) \in \mathcal{P}_{\text{param}}^k \quad (\text{ordered vector of auxiliary parameters}) \\
p_{\text{verdict}} &\in \mathcal{P}_{\text{param}} \quad (\text{mandatory formal verdict result parameter with } \tau(p_{\text{verdict}}) \equiv \text{VerdictKind}) \\
\Delta_{VD} &\in \Sigma^{36} \quad (\text{deterministic RFC 4122 UUIDv5 topological anchor}) \\
\text{span}_{VD} &= \langle \text{file\_id}, p_{\text{start}}, p_{\text{end}}, \text{line}, \text{col} \rangle \quad (\text{source lexical provenance})
\end{aligned}
```

  Each formal parameter $`p \in \mathbf{P}_{\text{subj}} \cup \mathbf{P}_{\text{param}} \cup \{ p_{\text{verdict}} \}`$ is formalized as:

```math
p = \langle \text{id}_p, \text{name}_p, \delta(p), \tau(p), \mu(p), \Delta_p \rangle
```

  where $`\delta(p) \in \{ \text{In}, \text{Out}, \text{InOut} \}`$`, `$`\tau(p) \in \mathcal{T}`$`, and `$`\mu(p) = [m_{\min}(p), m_{\max}(p)]`$.

  Subject Directionality Invariant: Formal subject parameters must possess input or bidirectional polarity:

```math
\forall s \in \mathbf{P}_{\text{subj}}, \quad \delta(s) \in \{ \text{In}, \text{InOut} \}
```

  Verdict Parameter Directionality and Type Invariant: The verdict parameter must possess output polarity and type `VerdictKind`:

```math
\delta(p_{\text{verdict}}) = \text{Out} \;\wedge\; \tau(p_{\text{verdict}}) \equiv \text{VerdictKind}
```

  Each verification usage $`VU \in \mathcal{VU}`$ is formalized as an 8-tuple:

```math
VU = \langle \text{id}_{VU}, \text{name}_{VU}, \text{owner}_{VU}, \tau(VU), \mathbf{A}_{\text{subj}}, \mathbf{A}_{\text{param}}, \mathcal{R}_{\text{verify}}, \Delta_{VU}, \text{span}_{VU} \rangle
```

  where:

```math
\begin{aligned}
\text{id}_{VU} &\in \mathbb{N}_{32} \quad (\text{contiguous arena node handle}) \\
\text{name}_{VU} &\in \mathcal{S}_{\text{intern}} \quad (\text{interned symbol identifier}) \\
\text{owner}_{VU} &\in \mathcal{C} \quad (\text{featuring classifier definition}) \\
\tau(VU) &\in \mathcal{VD} \quad (\text{referenced verification case definition handle}) \\
\mathbf{A}_{\text{subj}} &= (a_{s_1}, \dots, a_{s_j}) \in \mathcal{E}_{\text{expr}}^j \quad (\text{actual subject bindings}) \\
\mathbf{A}_{\text{param}} &= (a_1, \dots, a_k) \in \mathcal{E}_{\text{expr}}^k \quad (\text{actual auxiliary argument expressions}) \\
\mathcal{R}_{\text{verify}} &\subset \mathcal{VU} \times \mathcal{RD} \quad (\text{set of explicit requirement verification relationships}) \\
\Delta_{VU} &\in \Sigma^{36} \quad (\text{deterministic RFC 4122 UUIDv5 topological anchor}) \\
\text{span}_{VU} &= \langle \text{file\_id}, p_{\text{start}}, p_{\text{end}}, \text{line}, \text{col} \rangle \quad (\text{source lexical provenance})
\end{aligned}
```

  Subject Argument Subtyping Conformance Invariant: For every verification usage $`VU`$` referencing `$`VD = \tau(VU)`$, the actual subject arguments must conform to the declared subject parameter types:

```math
\Phi_{\text{subj\_conformance}}(VU, VD) \iff (|\mathbf{A}_{\text{subj}}| = |\mathbf{P}_{\text{subj}}|) \wedge \left( \bigwedge_{i=1}^j (\tau(a_{s_i}) \le_{\text{sub}} \tau(s_i)) \wedge \text{IsReadable}(a_{s_i}) \right)
```

  Execution Verdict Evaluation Mapping: The verification execution mapping evaluates a verification case $`VD`$` over subject valuation `$`s \in \mathcal{S}_{\text{subject}}`$` in environment state `$`\sigma`$:

```math
\text{eval} : \mathcal{VD} \times \mathcal{S}_{\text{subject}} \times \Sigma \longrightarrow \mathcal{V} \times \Sigma
```

```math
\forall VD \in \mathcal{VD}, \forall s \in \mathcal{S}_{\text{subject}}, \quad \text{eval}(VD, s, \sigma) = \langle \nu, \sigma' \rangle \quad \text{where } \nu \in \mathcal{V}
```

  Requirement Verification & Certification Invariant: Let $`(VU, R) \in \mathcal{R}_{\text{verify}}`$` denote a verification relationship binding verification usage `$`VU`$` to requirement `$`R \in \mathcal{RD}`$`. The formal satisfaction status of requirement `$`R`$` with respect to subject `$`s`$ is governed by the tri-state verdict:

```math
\begin{aligned}
\text{Verified}(R, s) &\iff \forall (VU, R) \in \mathcal{R}_{\text{verify}}, \quad \pi_1(\text{eval}(\tau(VU), s, \sigma)) \equiv \text{Pass} \\
\text{Refuted}(R, s) &\iff \exists (VU, R) \in \mathcal{R}_{\text{verify}} : \pi_1(\text{eval}(\tau(VU), s, \sigma)) \equiv \text{Fail} \\
\text{Inconclusive}(R, s) &\iff \neg \text{Refuted}(R, s) \;\wedge\; \exists (VU, R) \in \mathcal{R}_{\text{verify}} : \pi_1(\text{eval}(\tau(VU), s, \sigma)) \equiv \text{Inconclusive}
\end{aligned}
```

  Verification Call Graph Acyclicity Invariant: Let $`\mathcal{E}_{\text{v\_dep}} \subset \mathcal{VD} \times \mathcal{VD}`$` denote the invocation dependency relation between verification cases. The transitive closure `$`\mathcal{E}_{\text{v\_dep}}^+`$ must be irreflexive:

```math
\forall VD \in \mathcal{VD}, \quad (VD, VD) \notin \mathcal{E}_{\text{v\_dep}}^+
```

  Deterministic RFC 4122 UUIDv5 Topological Identity Invariant (Architectural Directive 1):

```math
\begin{aligned}
\forall VD \in \mathcal{VD}, \quad \Delta_{VD} &= \text{UUIDv5}(\text{OID}_{\text{DEAP}}, \text{FQN}(VD)) \\
\forall VU \in \mathcal{VU}, \quad \Delta_{VU} &= \text{UUIDv5}(\text{OID}_{\text{DEAP}}, \text{FQN}(VU)) \\
\forall p \in \mathbf{P}_{\text{subj}} \cup \mathbf{P}_{\text{param}} \cup \{ p_{\text{verdict}} \}, \quad \Delta_p &= \text{UUIDv5}(\text{OID}_{\text{DEAP}}, \text{FQN}(p))
\end{aligned}
```

  Diagnostic Trigger Invariants: Violations of metamodel well-formedness, subject parameter directionality, subtyping conformance, or call graph acyclicity deterministically emit structured diagnostics in accordance with REQ-0191:

```math
\begin{aligned}
(\mathbf{P}_{\text{subj}} = \emptyset \;\vee\; \tau(p_{\text{verdict}}) \not\equiv \text{VerdictKind}) &\implies \text{Diagnostic}(VD, \text{DiagnosticCode::E0200}, \text{MalformedVerificationSignature}) \in \mathcal{D}_{\text{sink}} \\
\exists s \in \mathbf{P}_{\text{subj}} : \delta(s) = \text{Out} &\implies \text{Diagnostic}(s, \text{DiagnosticCode::E0201}, \text{InvalidSubjectParameterDirection}) \in \mathcal{D}_{\text{sink}} \\
\tau(a_{s_i}) \not\le_{\text{sub}} \tau(s_i) &\implies \text{Diagnostic}(a_{s_i}, \text{DiagnosticCode::E0202}, \text{SubjectTypeMismatch}) \in \mathcal{D}_{\text{sink}} \\
(VD, VD) \in \mathcal{E}_{\text{v\_dep}}^+ &\implies \text{Diagnostic}(VD, \text{DiagnosticCode::E0203}, \text{CircularVerificationDependency}) \in \mathcal{D}_{\text{sink}} \\
\exists (VU, R) \in \mathcal{R}_{\text{verify}} : R \notin \mathcal{RD} &\implies \text{Diagnostic}(VU, \text{DiagnosticCode::E0200}, \text{UnresolvedRequirementReference}) \in \mathcal{D}_{\text{sink}} \\
|\mathcal{D}_{\text{sink}}| \ge C_{\text{max\_errors}} &\implies \exists D_{\text{term}} \in \mathcal{D}_{\text{sink}} : \text{code}(D_{\text{term}}) = \text{DiagnosticCode::E0199}
\end{aligned}
```

#### 3. Computational Complexity & Algorithmic Bounds

Lowering, signature verification, and static semantic typing of SysML v2 `VerificationCaseDefinition` and `VerificationUsage` AST nodes execute strictly within Complexity Class $`\mathbf{P}`$.

  The operational complexity bounds are formalized as follows:
  1. *AST Arena Allocation & Symbol Interning*: Allocating each `VerificationCaseDefinition`, `VerificationUsage`, `Parameter`, and `VerifyRelationship` node into contiguous bump arena storage and interning symbol identifiers requires amortized $`O(1)`$` time and `$`O(1)`$ auxiliary heap space.
  2. *Subject Parameter & Signature Verification*: Validating subject parameter directionality $`\delta(s) \in \{ \text{In}, \text{InOut} \}`$`, parameter arity, and verdict output return type `$`\tau(p_{\text{verdict}}) \equiv \text{VerdictKind}`$` executes in `$`O(|\mathbf{P}_{\text{subj}}| + |\mathbf{P}_{\text{param}}|)`$` operations. Since parameter cardinality is bounded by specification design (`$`j + k \le 16 = O(1)`$`), signature validation executes in strictly `$`O(1)`$ time per verification definition.
  3. *Subject Binding & Subtyping Conformance*: For each verification usage binding $`j`$` subject arguments and `$`k`$` auxiliary parameters, verifying arity and checking subtyping conformance `$`\tau(a_{s_i}) \le_{\text{sub}} \tau(s_i)`$` executes in `$`O(1)`$` time using precomputed subtyping bitsets or bounded lattice traversal (`$`h \le 32`$).
  4. *Traceability Binding to Requirements*: Resolving and binding each $`(VU, R)`$` verify relationship edge executes in `$`O(1)`$ time via scoped symbol table lookup.
  5. *Verification Call Graph Acyclicity Checking*: Evaluating acyclicity over the call graph $`\mathcal{G}_{\text{v\_dep}} = (\mathcal{VD}, \mathcal{E}_{\text{v\_dep}})`$` using Tarjan's strongly connected components algorithm or Kahn's topological sort executes in deterministic `$`O(|\mathcal{VD}| + |\mathcal{E}_{\text{v\_dep}}|)`$ time.
  6. *Verification Case Dispatch & Verdict Recording*: Dispatching a verification case execution and recording the resulting tri-state verdict executes in $`O(1)`$ state machine updates per execution run.
  7. *Aggregate Compilation Unit Complexity*: For a compilation unit containing $`N = |\mathcal{VD}|`$` verification case definitions and `$`M = |\mathcal{VU}|`$` verification usages with dependency edges `$`\mathcal{E}_{\text{v\_dep}}`$:

```math
T_{\text{validate}}(N, M, \mathcal{E}_{\text{v\_dep}}) \in O(N + M + |\mathcal{E}_{\text{v\_dep}}|)
```

  8. *Parallel Work-Stealing Scaling (Architectural Directive 2)*: When verification case lowering and validation across independent compilation packages are scheduled onto a bounded work-stealing thread pool with worker bound $`N_{\text{max\_workers}}`$:

```math
T_{\text{parallel}}(N, M, N_{\text{max\_workers}}) \in O\left( \frac{N + M + |\mathcal{E}_{\text{v\_dep}}|}{N_{\text{max\_workers}}} + \log N_{\text{max\_workers}} \right)
```

  9. *Memory Bounds*: Auxiliary memory is bounded by $`O(N + M)`$` arena storage for lowered AST nodes. Verification call stacks are bounded by recursion depth cutoff `$`O(d_{\max})`$` where `$`d_{\max} \le 64 = O(1)`$` frames. The diagnostic error sink buffer is strictly bounded by `$`O(C_{\text{max\_errors}}) = O(1)`$ allocated memory.

#### 4. Verification & Conformance Criteria

Automated test suites shall deterministically verify compliance against synthetic abstract MBSE models (`Package_0`, `Classifier_Alpha`, `Classifier_Beta`, `VerificationDef_Alpha`, `VerificationDef_Beta`, `VerificationUsage_1`, `VerificationUsage_2`, `Requirement_1`, `Requirement_2`, `param_x : Real`, `param_y : Real`, `verdict_val : VerdictKind`) across the following verification gates:
  1. **Canonical `verification def` & `verification` Usage Lowering Gate**: Define `verification def VerificationDef_Alpha { subject item_under_test : Classifier_Alpha; in param_x : Real; out verdict : VerdictKind; }` and instantiate `verification VerificationUsage_1 : VerificationDef_Alpha { subject = Classifier_Alpha_Instance; param_x = 10.0; }` within `Package_0`. Assert 100% lowering into contiguous bump arena storage, valid parameter bindings, and zero diagnostics emitted.
  2. **Dual Inheritance Specialization Gate**: Declare `verification def VerificationDef_Alpha`. Ingest the model and assert that the lowered AST node exhibits specialization edges to KerML `Behavior` and SysML v2 `CaseDefinition`, verifying correct feature inheritance and occurrence lifecycle semantics with zero diagnostics emitted.
  3. **Mandatory Tri-State Verdict Codomain Gate (`E0200`)**: Declare a verification definition lacking a verdict output parameter or declaring an invalid non-verdict return type (e.g., returning `Real` instead of `VerdictKind`). Assert deterministic compile-time rejection with diagnostic error code `E0200` (`MalformedVerificationSignature`) and assignment of error sentinel $`\bot_{\text{verif}}`$.
  4. **Subject Parameter Directionality Gate (`E0201`)**: Declare a verification case definition where the formal subject parameter is explicitly declared with `out` directionality (`out subject item_under_test : Classifier_Alpha`). Assert deterministic compile-time rejection with diagnostic error code `E0201` (`InvalidSubjectParameterDirection`).
  5. **Subject Argument Subtyping Conformance Gate (`E0202`)**: Instantiate `VerificationDef_Alpha` binding a subject argument of type `Classifier_Beta` where `Classifier_Beta` does not specialize `Classifier_Alpha`. Assert deterministic compile-time rejection with diagnostic error code `E0202` (`SubjectTypeMismatch`). Inject a conforming subtype and assert successful compilation with zero diagnostics.
  6. **Requirement Verification Traceability Binding Gate**: Declare requirement `Requirement_1` and bind `verification VerificationUsage_1 : VerificationDef_Alpha { subject = Classifier_Alpha_Instance; verify requirement Requirement_1; }`. Assert that the lowering engine establishes a directed traceability edge $`(\text{VerificationUsage\_1}, \text{Requirement\_1}) \in \mathcal{R}_{\text{verify}}`$. Bind to an unresolvable requirement name and assert deterministic rejection with diagnostic error code `E0200` (`UnresolvedRequirementReference`).
  7. **Tri-State Verdict Execution & State Machine Dispatch Gate**: In a simulation or test runner execution environment, dispatch verification cases producing verdicts `Pass`, `Fail`, and `Inconclusive`. Assert that dispatch and verdict recording execute in $`O(1)`$ state machine updates per execution run, certifying `Requirement_1` as verified if and only if verdict is `Pass`, refuted if `Fail`, and unverified if `Inconclusive`.
  8. **Circular Verification Dependency Cycle Detection Gate (`E0203`)**: Declare mutually recursive verification cases where `VerificationDef_Alpha` invokes `VerificationDef_Beta` and `VerificationDef_Beta` invokes `VerificationDef_Alpha`. Assert that topological cycle detection identifies the cycle and emits diagnostic error code `E0203` (`CircularVerificationDependency`) with exact source byte spans for all participating definitions.
  9. **Verification Step Assertion Failure Gate**: In an execution scenario with embedded `assert constraint`, trigger a constraint failure during verification step execution. Assert that the verification runtime transitions the intermediate verdict to `Fail` and emits a structured verification failure report.
  10. **Synchronization Token Error Recovery & Error Accumulation Gate (Architectural Directive 4)**: Ingest a model unit containing 5 distinct malformed verification declarations interspersed with valid code. Verify that the lowering engine resynchronizes on delimiter boundaries, accumulates all 5 `E0200`, `E0201`, `E0202`, and `E0203` diagnostics into $`\mathcal{D}_{\text{sink}}`$, and halts gracefully with terminal diagnostic `E0199` when the error count reaches $`C_{\text{max\_errors}}`$.
  11. **Bounded Work-Stealing Parallelism Gate (Architectural Directive 2)**: Concurrently lower and verify $`10^4`$` synthetic verification definitions across `$`N_{\text{max\_workers}}`$ threads in the bounded work-stealing pool. Assert data-race freedom, zero deadlocks, and 100% bitwise identical diagnostic outputs compared to single-threaded sequential execution.
  12. **Deterministic UUIDv5 & Performance Budget Gate (Architectural Directives 1 & 5)**: In compiled Release mode (`--release`) under dedicated benchmark harnesses isolated from CI logic tests per REQ-0011 and REQ-0196, assert that lowering and verifying $`10^5`$ synthetic verification definitions and usages executes in strictly under 25 ms, peak RSS memory remains strictly under 100 MB, all nodes receive deterministic RFC 4122 UUIDv5 identifiers, and consecutive compilation runs exhibit bitwise determinism with 0-byte diff churn.
