### REQ-0085: SysML v2 RequirementDefinition (`requirement def`) & RequirementUsage Lowering

- **Normative Statement**: The KerML/SysML v2 metamodel lowering engine and semantic type checker of Subsystem 4 shall formalize SysML v2 requirement definitions (`RequirementDefinition`, denoted by keyword `requirement def`) and requirement usages (`RequirementUsage`, denoted by keyword `requirement`) as structured contractual specification classifiers specializing KerML `ConstraintDefinition` and `ConstraintUsage`. Every `RequirementDefinition` shall define a formal contractual specification possessing an interned alphanumeric identifier, a normative textual specification prose block, an explicit formal subject parameter, an optional environment assumption predicate, and one or more mandatory postcondition guarantee predicates.

  The compiler shall strictly enforce the following structural, typing, and semantic invariants during requirement lowering:
  1. **Metamodel Classifier Specialization**: In the KerML and SysML v2 metamodel taxonomy, `RequirementDefinition` specializes `ConstraintDefinition`, which in turn specializes KerML `Predicate` and `Function` ($\text{RequirementDef} \le_{\text{sub}} \text{ConstraintDef} \le_{\text{sub}} \text{Predicate} \le_{\text{sub}} \text{Function} \longrightarrow \mathbb{B}$). Every `RequirementUsage` specializes `ConstraintUsage` and `Feature` ($\text{RequirementUsage} \le_{\text{sub}} \text{ConstraintUsage} \le_{\text{sub}} \text{Feature}$), representing the contextual application or feature instantiation of a requirement contract within an enclosing classifier definition (e.g., `part def`, `item def`, `action def`) or package.
  2. **Global Alphanumeric Identifier Uniqueness**: Every `RequirementDefinition` and `RequirementUsage` shall declare or be assigned an alphanumeric requirement identifier token $\text{req\_id} \in \mathcal{S}_{\text{intern}}$ (e.g., `REQ-0085`, `SYS_REQ_01`). The compiler shall maintain a global deduplicated identifier symbol table across all compilation units within the repository and statically verify that requirement identifiers are globally unique ($\forall R_1 \ne R_2, \text{req\_id}(R_1) \ne \text{req\_id}(R_2)$). Declaration of duplicate requirement identifiers within or across compilation units shall be deterministically rejected at compile time with diagnostic error code `E0200` (`DuplicateRequirementIdentifier`) in accordance with REQ-0191.
  3. **Normative Text Contract Preservation**: Every `RequirementDefinition` shall specify a non-empty normative text contract describing the specification intent in structured prose. The compiler shall ingest the text literal into the global symbol interner pool as a deduplicated interned string without loss of lexical formatting or character content. Empty textual contract specifications shall be rejected with diagnostic error code `E0200` (`EmptyRequirementText`).
  4. **Subject Parameter Declaration & Binding Invariants**: Every `RequirementDefinition` shall declare at least one formal `subject` parameter ($p_{\text{subject}}$) characterizing the system element, component, or occurrence bounded by the contractual obligation. The subject parameter must declare or default to immutable `In` directionality ($\text{dir}(p_{\text{subject}}) \equiv \text{In}$). Declaring an `Out` or `InOut` subject parameter shall be rejected with diagnostic error code `E0201` (`InvalidRequirementParameterDirection`). In every `RequirementUsage`, the subject parameter must be explicitly bound to an actual argument expression or accessible model element within scope ($a_{\text{subject}}$), and the compiler shall verify that the evaluated type of $a_{\text{subject}}$ specializes or unifies with the declared subject parameter type in the subtyping semilattice ($\tau(a_{\text{subject}}) \le_{\text{sub}} \tau(p_{\text{subject}})$). Missing subject argument bindings or type incompatibility shall be rejected with diagnostic error code `E0200` (`SubjectBindingMismatch`).
  5. **Assume-Guarantee Predicate Contract Semantics**: A requirement contract models a formal assume-guarantee contract $\mathcal{C}_R = (\mathcal{A}_{\text{assume}}, \mathcal{G}_{\text{require}})$:
     - The environment assumption $\mathcal{A}_{\text{assume}}$ consists of zero or more `assume` constraint expressions defining preconditions that the operational environment or calling context must satisfy. If no assumption is explicitly declared, $\mathcal{A}_{\text{assume}}$ defaults to constant tautology $\top$ (`true`).
     - The requirement guarantee $\mathcal{G}_{\text{require}}$ consists of one or more `require` constraint expressions defining mandatory postconditions and invariant properties guaranteed by the subject realization under assumption $\mathcal{A}_{\text{assume}}$.
     - The semantic type checker shall statically verify that all expressions in `assume` and `require` blocks evaluate to primitive `Boolean` ($\tau(e) \equiv \text{Boolean}$). Expressions evaluating to non-Boolean types shall be rejected with diagnostic error code `E0200` (`NonBooleanRequirementPredicate`).
     - The contract imposes the formal implication $\mathcal{A}_{\text{assume}}(\sigma) \implies \mathcal{G}_{\text{require}}(\sigma)$ across all admissible system configurations $\sigma \in \Sigma_{\text{valid}}$.
  6. **Functional Purity & Side-Effect Freedom**: Formal parameters, assumptions, and guarantees of a requirement contract shall be strictly immutable and functionally pure ($\Delta \text{State} \equiv \emptyset$). Any assignment, mutable state access, or invocation of non-functional behaviors within a requirement body shall be rejected at compile time with diagnostic error code `E0200` (`ImpureRequirementExpression`).
  7. **Formal Parameter Signature & Argument Conformance**: A requirement definition may declare additional formal parameters $\mathbf{P}_{\text{param}} = (p_1, \dots, p_k)$ specifying operational thresholds, bounds, or context variables. All formal parameters must declare `In` directionality ($\text{dir}(p_i) \equiv \text{In}$), with non-`In` directionalities rejected with diagnostic error code `E0201`. In a requirement usage, actual argument expressions $\mathbf{A}_{\text{param}} = (a_1, \dots, a_m)$ must match parameter arity ($m = k$) and satisfy subtyping conformance ($\tau(a_i) \le_{\text{sub}} \tau(p_i)$), with violations rejected with diagnostic error code `E0200` (`ParameterBindingMismatch`).
  8. **Hierarchical Decomposition & Acyclic Call Graph**: Requirements may be hierarchically decomposed through nested composite requirement usages (`requirement sub_req : ...`), subsetting (`:>` / REQ-0061), or redefinition (`:>>` / REQ-0062). The lowering engine shall construct a directed dependency multigraph $\mathcal{G}_{\text{req\_dep}} = (\mathcal{RD} \cup \mathcal{RU}, \mathcal{R}_{\text{req\_dep}})$ tracking sub-requirement containment and definition references. Circular requirement dependencies ($R_1 \to R_2 \to \dots \to R_1$) shall be strictly prohibited and detected via topological sorting (Tarjan's strongly connected components algorithm or Kahn's in-degree reduction), emitting diagnostic error code `E0203` (`CircularRequirementDependency`).
  9. **Anonymous & Shorthand Requirement Lowering**: When a model declares an anonymous requirement shorthand block (`requirement { doc /* text */ ... require { ... } }`), the lowering engine shall synthesize an anonymous `RequirementDefinition` node in contiguous bump arena storage with `Anonymous` discriminant kind, synthesize formal parameters for free variables and subject references, bind them to a synthesized `RequirementUsage` node, and register the generated entities with deterministic UUIDv5 identifiers.

  **Architectural Directives Compliance**:
  - *Directive 1 (Deterministic UUIDv5 Anchors)*: Every lowered `RequirementDefinition`, `RequirementUsage`, parameter, assume clause, and require clause AST node shall be assigned an immutable deterministic RFC 4122 UUIDv5 identifier generated by namespace-hashing the fully qualified symbol path (e.g., `Package_0::Classifier_Alpha::Requirement_1`) with the canonical compiler namespace OID per REQ-0010.
  - *Directive 2 (Bounded Work-Stealing Parallelism)*: Parallel lowering, AST arena allocation, and semantic contract validation of independent requirement definitions and usages across distinct compilation packages shall execute strictly on a bounded work-stealing thread pool with worker bound $N_{\text{max\_workers}}$ per REQ-0012.
  - *Directive 3 (String Interner Allocation Exception)*: Scalar requirement identifiers (`req_id`), symbol names, qualified paths, and normative specification text bytes shall be interned into the global deduplicated symbol interner pool per REQ-0036 as the sole permitted exception to zero-copy memory management.
  - *Directive 4 (Synchronization Token Error Recovery)*: The lowering engine shall implement synchronization token error recovery on requirement declaration boundaries and semicolon delimiters per REQ-0013 and REQ-0016. Upon encountering a syntax fault, duplicate identifier (`E0200`), parameter direction mismatch (`E0201`), or circular dependency (`E0203`), the engine shall record the diagnostic into the error sink buffer $\mathcal{D}_{\text{sink}}$, substitute an error sentinel node $\bot_{\text{req}}$, and resynchronize on the next declaration delimiter without aborting compilation. If accumulated diagnostics reach the preallocated capacity limit $C_{\text{max\_errors}}$, the compiler shall emit terminal diagnostic `E0199` and halt gracefully.
  - *Directive 5 (Panic-Free Release Isolation)*: Production compiler library code shall enforce a deterministic, non-panicking execution contract with total-function termination across all valid and malformed inputs. Execution latency ($\lt 25\text{ ms}$) and peak memory RSS ($\lt 100\text{ MB}$ for $10^5$ requirement nodes) performance gates shall be evaluated exclusively in compiled Release mode (`--release`) under dedicated benchmark harnesses isolated from CI logic tests per REQ-0011 and REQ-0196.

  All diagnostic messages, test models, and illustrative examples shall strictly employ synthetic abstract MBSE placeholders (`Package_0`, `Classifier_Alpha`, `Classifier_Beta`, `RequirementDef_Alpha`, `RequirementDef_Beta`, `RequirementUsage_1`, `RequirementUsage_2`, `Subject_0`, `param_x : Real`, `param_y : Real`, `attr_a : Real`, `attr_b : Real`), strictly prohibiting hardcoded domain concepts, mock data, and non-ASCII dashes.

- **Formal Invariant**: Let $\mathcal{V}_{\text{AST}}$ denote the universe of allocated AST nodes in contiguous bump arena storage. Let $\mathcal{RD} \subset \mathcal{V}_{\text{AST}}$ denote the set of requirement definition nodes, and let $\mathcal{RU} \subset \mathcal{V}_{\text{AST}}$ denote the set of requirement usage nodes.

  The specialization taxonomy of `RequirementDefinition` and `RequirementUsage` within the KerML metamodel poset ordered by subtyping relation $\le_{\text{sub}}$ satisfies:

$$
\text{RequirementDef} \le_{\text{sub}} \text{ConstraintDef} \le_{\text{sub}} \text{Predicate} \le_{\text{sub}} \text{Function}
$$

$$
\text{RequirementUsage} \le_{\text{sub}} \text{ConstraintUsage} \le_{\text{sub}} \text{Feature}
$$

  Each requirement definition $RD \in \mathcal{RD}$ is formalized as a 12-tuple:

$$
RD = \langle \text{node\_id}_{RD}, \text{req\_id}_{RD}, \text{name}_{RD}, \text{owner}_{RD}, p_{\text{subject}}, \mathbf{P}_{RD}, \text{text}_{RD}, e_{\text{assume}}, e_{\text{require}}, \kappa_{RD}, \Delta_{RD}, \text{span}_{RD} \rangle
$$

  where:

$$
\begin{aligned}
\text{node\_id}_{RD} &\in \mathbb{N}_{32} \quad (\text{contiguous arena node handle}) \\
\text{req\_id}_{RD} &\in \mathcal{S}_{\text{intern}} \quad (\text{interned global alphanumeric identifier}) \\
\text{name}_{RD} &\in \mathcal{S}_{\text{intern}} \quad (\text{interned symbol name identifier}) \\
\text{owner}_{RD} &\in \mathcal{C} \cup \mathcal{P}_{\text{pkg}} \quad (\text{owning classifier definition or package}) \\
p_{\text{subject}} &\in \mathcal{V}_{\text{param}} \quad (\text{formal subject parameter handle}) \\
\mathbf{P}_{RD} &= (p_1, \dots, p_k) \in \mathcal{V}_{\text{param}}^k \quad (\text{ordered formal parameter handles}) \\
\text{text}_{RD} &\in \mathcal{S}_{\text{intern}} \quad (\text{interned normative prose specification}) \\
e_{\text{assume}} &\in \mathcal{E}_{\text{expr}} \cup \{ \top \} \quad (\text{assumption predicate expression root}) \\
e_{\text{require}} &\in \mathcal{E}_{\text{expr}} \quad (\text{guarantee predicate expression root}) \\
\kappa_{RD} &\in \{ \text{Named}, \text{Anonymous} \} \quad (\text{definition syntactic form}) \\
\Delta_{RD} &\in \Sigma^* \quad (\text{deterministic RFC 4122 UUIDv5 topological anchor}) \\
\text{span}_{RD} &= \langle \text{file\_id}, p_{\text{start}}, p_{\text{end}}, \text{line}, \text{col} \rangle \quad (\text{source lexical provenance})
\end{aligned}
$$

  Each formal parameter $p_i \in \{ p_{\text{subject}} \} \cup \mathbf{P}_{RD}$ is formalized as:

$$
p_i = \langle \text{node\_id}_{p_i}, \text{name}_{p_i}, \tau(p_i), \mu(p_i), \text{dir}(p_i) \rangle
$$

  where $\text{dir}(p_i) \equiv \text{In}$, $\tau(p_i) \in \mathcal{T} \setminus \{ \bot_{\text{type}} \}$, and $\mu(p_i) = [m_{\min}, m_{\max}]$.

  Each requirement usage $RU \in \mathcal{RU}$ is formalized as a 9-tuple:

$$
RU = \langle \text{node\_id}_{RU}, \text{req\_id}_{RU}, \text{name}_{RU}, \text{owner}_{RU}, \tau(RU), a_{\text{subject}}, \mathbf{A}_{RU}, \Delta_{RU}, \text{span}_{RU} \rangle
$$

  where:

$$
\begin{aligned}
\text{node\_id}_{RU} &\in \mathbb{N}_{32} \quad (\text{contiguous arena node handle}) \\
\text{req\_id}_{RU} &\in \mathcal{S}_{\text{intern}} \quad (\text{interned global alphanumeric identifier}) \\
\text{name}_{RU} &\in \mathcal{S}_{\text{intern}} \quad (\text{interned symbol name identifier}) \\
\text{owner}_{RU} &\in \mathcal{C} \cup \mathcal{RD} \quad (\text{featuring classifier or composite requirement}) \\
\tau(RU) &\in \mathcal{RD} \quad (\text{referenced requirement definition handle}) \\
a_{\text{subject}} &\in \mathcal{E}_{\text{expr}} \quad (\text{actual subject argument binding}) \\
\mathbf{A}_{RU} &= (a_1, \dots, a_m) \in \mathcal{E}_{\text{expr}}^m \quad (\text{actual argument expressions}) \\
\Delta_{RU} &\in \Sigma^* \quad (\text{deterministic RFC 4122 UUIDv5 topological anchor}) \\
\text{span}_{RU} &= \langle \text{file\_id}, p_{\text{start}}, p_{\text{end}}, \text{line}, \text{col} \rangle \quad (\text{source lexical provenance})
\end{aligned}
$$

  Subject and Parameter Directionality Invariant: All formal parameters of a requirement definition, including the mandatory subject parameter, must have strictly `In` directionality:

$$
\text{dir}(p_{\text{subject}}) \equiv \text{In} \;\wedge\; \forall p \in \mathbf{P}_{RD}, \quad \text{dir}(p) \equiv \text{In}
$$

  Functional Purity & Side-Effect Freedom Invariant: Evaluating assume and guarantee expressions produces zero mutation on system state $\sigma \in \Sigma$:

$$
\forall \sigma \in \Sigma, \quad \llbracket e_{\text{assume}} \rrbracket(\sigma) = \langle v_{\text{assume}}, \sigma \rangle \;\wedge\; \llbracket e_{\text{require}} \rrbracket(\sigma) = \langle v_{\text{require}}, \sigma \rangle \quad \text{where } v_{\text{assume}}, v_{\text{require}} \in \mathbb{B}
$$

  Predicate Codomain Invariant: Both assumption and guarantee expressions must statically evaluate to type `Boolean`:

$$
\Phi_{\text{codomain}}(RD) \iff (\tau(e_{\text{assume}}) \equiv \text{Boolean}) \wedge (\tau(e_{\text{require}}) \equiv \text{Boolean})
$$

  Assume-Guarantee Contract Semantics Invariant: Across all admissible system configurations $\sigma \in \Sigma_{\text{valid}}$, satisfaction of the environment assumption implies satisfaction of the requirement guarantee:

$$
\forall \sigma \in \Sigma_{\text{valid}}, \quad \llbracket e_{\text{assume}} \rrbracket(\sigma) \implies \llbracket e_{\text{require}} \rrbracket(\sigma)
$$

  Global Requirement Identifier Uniqueness Invariant: All requirement identifiers across all requirement definitions and usages within the compilation repository must be distinct:

$$
\forall R_1, R_2 \in \mathcal{RD} \cup \mathcal{RU}, \quad (R_1 \ne R_2) \implies (\text{req\_id}(R_1) \ne \text{req\_id}(R_2))
$$

  Subject Binding & Subtyping Conformance Invariant: For every requirement usage $RU \in \mathcal{RU}$ referencing definition $RD = \tau(RU)$, the subject argument $a_{\text{subject}}$ must conform to the subject parameter type:

$$
\Phi_{\text{subject\_binding}}(RU, RD) \iff (\tau(a_{\text{subject}}) \le_{\text{sub}} \tau(p_{\text{subject}})) \wedge \text{IsReadable}(a_{\text{subject}})
$$

  Parameter Binding & Subtyping Conformance Invariant: For every requirement usage $RU \in \mathcal{RU}$ referencing definition $RD = \tau(RU)$, the argument vector $\mathbf{A}_{RU} = (a_1, \dots, a_m)$ must match the formal parameter vector $\mathbf{P}_{RD} = (p_1, \dots, p_k)$ in arity and type conformance:

$$
\Phi_{\text{param\_binding}}(RU, RD) \iff (m = k) \wedge \left( \bigwedge_{i=1}^k (\tau(a_i) \le_{\text{sub}} \tau(p_i)) \wedge \text{IsReadable}(a_i) \right)
$$

  Requirement Call Graph & Decomposition Acyclicity Invariant: Let $\mathcal{R}_{\text{req\_dep}} \subset (\mathcal{RD} \cup \mathcal{RU}) \times (\mathcal{RD} \cup \mathcal{RU})$ denote the requirement dependency and containment relation. The transitive closure $\mathcal{R}_{\text{req\_dep}}^+$ must be irreflexive:

$$
\forall R \in \mathcal{RD} \cup \mathcal{RU}, \quad (R, R) \notin \mathcal{R}_{\text{req\_dep}}^+
$$

  Deterministic RFC 4122 UUIDv5 Topological Identity Invariant:

$$
\begin{aligned}
\forall RD \in \mathcal{RD}, \quad \Delta_{RD} &= \text{UUIDv5}(\text{OID}_{\text{DEAP}}, \text{FQN}(RD)) \\
\forall RU \in \mathcal{RU}, \quad \Delta_{RU} &= \text{UUIDv5}(\text{OID}_{\text{DEAP}}, \text{FQN}(RU))
\end{aligned}
$$

  Diagnostic Trigger Invariants: Violations of identifier uniqueness, predicate codomain, parameter directionality, subject binding, parameter binding, or dependency acyclicity deterministically emit structured diagnostics per REQ-0191:

$$
\begin{aligned}
\exists R_1 \ne R_2 : \text{req\_id}(R_1) = \text{req\_id}(R_2) &\implies \text{Diagnostic}(R_2, \text{DiagnosticCode::E0200}, \text{DuplicateRequirementIdentifier}) \in \mathcal{D}_{\text{sink}} \\
\neg \Phi_{\text{codomain}}(RD) &\implies \text{Diagnostic}(RD, \text{DiagnosticCode::E0200}, \text{NonBooleanRequirementPredicate}) \in \mathcal{D}_{\text{sink}} \\
\text{dir}(p_{\text{subject}}) \ne \text{In} \;\vee\; \exists p \in \mathbf{P}_{RD} : \text{dir}(p) \ne \text{In} &\implies \text{Diagnostic}(p, \text{DiagnosticCode::E0201}, \text{InvalidRequirementParameterDirection}) \in \mathcal{D}_{\text{sink}} \\
\neg \Phi_{\text{subject\_binding}}(RU, \tau(RU)) &\implies \text{Diagnostic}(RU, \text{DiagnosticCode::E0200}, \text{SubjectBindingMismatch}) \in \mathcal{D}_{\text{sink}} \\
\neg \Phi_{\text{param\_binding}}(RU, \tau(RU)) &\implies \text{Diagnostic}(RU, \text{DiagnosticCode::E0200}, \text{ParameterBindingMismatch}) \in \mathcal{D}_{\text{sink}} \\
(R, R) \in \mathcal{R}_{\text{req\_dep}}^+ &\implies \text{Diagnostic}(R, \text{DiagnosticCode::E0203}, \text{CircularRequirementDependency}) \in \mathcal{D}_{\text{sink}} \\
|\mathcal{D}_{\text{sink}}| \ge C_{\text{max\_errors}} &\implies \exists D_{\text{term}} \in \mathcal{D}_{\text{sink}} : \text{code}(D_{\text{term}}) = \text{DiagnosticCode::E0199}
\end{aligned}
$$

- **Computational Complexity & Algorithmic Bounds**: Lowering and semantic verification of `RequirementDefinition` and `RequirementUsage` AST nodes executes strictly within Complexity Class $\mathbf{P}$.

  The operational complexity bounds are formalized as follows:
  1. *AST Arena Allocation & Symbol Interning*: Allocating each `RequirementDefinition`, `RequirementUsage`, and `Parameter` node into contiguous bump arena storage and interning symbol identifiers and text contracts requires amortized $O(1)$ time and $O(1)$ auxiliary heap space.
  2. *Global Identifier Deduplication*: Inserting and verifying requirement identifiers $\text{req\_id}$ into the global symbol lookup table executes in amortized $O(1)$ time per requirement, yielding $O(N + M)$ total time for $N = |\mathcal{RD}|$ definitions and $M = |\mathcal{RU}|$ usages.
  3. *Predicate Expression Type Checking*: Validating the Boolean codomain $\tau(e_{\text{assume}}) \equiv \text{Boolean}$ and $\tau(e_{\text{require}}) \equiv \text{Boolean}$ traverses expression syntax trees in deterministic $O(|e_{\text{assume}}| + |e_{\text{require}}|)$ time.
  4. *Subject & Parameter Binding Conformance*: Verifying subject conformance $\tau(a_{\text{subject}}) \le_{\text{sub}} \tau(p_{\text{subject}})$ executes in $O(1)$ time. Verifying parameter arity and checking subtyping conformance $\tau(a_i) \le_{\text{sub}} \tau(p_i)$ for $k$ parameters executes in $O(k)$ time. Since parameter count is bounded by language design ($k \le 16 = O(1)$), binding verification requires $O(1)$ time per requirement usage.
  5. *Requirement Dependency & Decomposition Acyclicity Checking*: Evaluating acyclicity over the requirement dependency graph $\mathcal{G}_{\text{req\_dep}} = (\mathcal{RD} \cup \mathcal{RU}, \mathcal{R}_{\text{req\_dep}})$ using Tarjan's strongly connected components algorithm or Kahn's topological sort executes in deterministic $O(|\mathcal{RD}| + |\mathcal{RU}| + |\mathcal{R}_{\text{req\_dep}}|)$ time.
  6. *Grounded Contract Evaluation*: Evaluating assume and guarantee expressions over grounded state valuations $\sigma$ executes in $O(|e_{\text{assume}}| + |e_{\text{require}}|)$ stack operations, requiring strictly $O(1)$ stack operations per expression AST node.
  7. *Aggregate Compilation Unit Complexity*: For a compilation unit containing $N = |\mathcal{RD}|$ requirement definitions and $M = |\mathcal{RU}|$ requirement usages with total expression size $E_{\text{nodes}} = \sum_{j=1}^N (|e_{\text{assume}, j}| + |e_{\text{require}, j}|)$:

$$
T_{\text{validate}}(N, M, E_{\text{nodes}}, |\mathcal{R}_{\text{req\_dep}}|) \in O(N + M + E_{\text{nodes}} + |\mathcal{R}_{\text{req\_dep}}|)
$$

  8. *Parallel Work-Stealing Scaling (Architectural Directive 2)*: When requirement validation across disjoint compilation packages is scheduled onto a bounded work-stealing thread pool with worker bound $N_{\text{max\_workers}}$:

$$
T_{\text{parallel}}(N, M, N_{\text{max\_workers}}) \in O\left( \frac{N + M + E_{\text{nodes}} + |\mathcal{R}_{\text{req\_dep}}|}{N_{\text{max\_workers}}} + \log N_{\text{max\_workers}} \right)
$$

  9. *Memory Bounds*: Auxiliary memory is bounded by $O(N + M + E_{\text{nodes}})$ contiguous bump arena storage for lowered AST nodes. Global identifier table storage is bounded by $O(N + M)$. Expression evaluation call stacks are bounded by expression tree depth $O(d_{\max})$ where $d_{\max} \le 64 = O(1)$ frames. The diagnostic error sink buffer is strictly bounded by $O(C_{\text{max\_errors}}) = O(1)$ preallocated memory.

- **Verification & Conformance Criteria**: Automated test suites shall deterministically verify compliance against synthetic abstract MBSE models (`Package_0`, `Classifier_Alpha`, `Classifier_Beta`, `RequirementDef_Alpha`, `RequirementDef_Beta`, `RequirementUsage_1`, `RequirementUsage_2`, `Subject_0`, `param_x : Real`, `param_y : Real`, `attr_a : Real`, `attr_b : Real`) across the following verification gates:

  3. **Non-Boolean Assume / Require Predicate Typing Gate (`E0200`)**: Declare a requirement definition whose assume or require expression evaluates to a non-Boolean type (e.g., an arithmetic Real sum `Subject_0.attr_a + Subject_0.attr_b`).   4. **Subject Parameter Declaration & Binding Conformance Gate (`E0200`)**: Instantiate a requirement usage without binding the mandatory subject parameter, or binding an actual argument whose type does not conform to the declared subject parameter type ($\tau(a_{\text{subject}}) \not\le_{\text{sub}} \tau(p_{\text{subject}})$). Assert that evaluation yields `false` and triggers a structured contract violation event identifying the failing coordinate values. When grounded with an assumption evaluating to `false`, assert vacuous contract satisfaction with no violation event.
  11. **Synchronization Token Error Recovery & Error Accumulation Gate (Architectural Directive 4)**: Ingest a model unit containing 5 distinct malformed requirement declarations interspersed with valid code. Verify that the lowering engine resynchronizes on delimiter boundaries, accumulates all 5 `E0200` and `E0201` diagnostics with precise source spans, and halts gracefully with terminal diagnostic `E0199` when the error count reaches $C_{\text{max\_errors}}$.
